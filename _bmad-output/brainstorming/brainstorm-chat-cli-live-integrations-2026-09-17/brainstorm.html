Technique 01 — Six Thinking Hats

Six lenses, one question

Before any idea got judged, the same question — what should Yoh be allowed to actually do? — passed through six deliberately separate modes of thinking. Facts first, then feelings, then benefits, risks, new ideas, and finally process.

White
Facts
  • Notion adapter today only does readNotionTasks/setTaskStatus/updateTaskField — narrow, schema-bound writes, no arbitrary page or DB creation.
  • Calendar adapter already reads events and writes the daily plan to a dedicated 'Yoh Plan' calendar, but doesn't read/write the user's main calendar for ad hoc time-blocking.
  • chat-cli.ts is currently a deterministic command parser (parseTimeBudgetCommand, parseFieldAnswer, etc.), not a freeform LLM tool-calling loop.
  • There is no existing search/browsing capability anywhere in the codebase — web search would be wholly new surface area.
  • FR-24 already established the precedent of chat-cli writing missing planning fields back to Notion live from a chat turn.
Red
Feelings
  • Excited: turns Yoh from a read-mostly planner into an actual doer — 'add a task and put it on my calendar' becomes one sentence instead of three app-switches.
  • Nervous: broad write access is the first time a bug or hallucination could silently corrupt real data the user depends on daily.
  • Relief-seeking: web search finally lets Yoh answer factual questions without the user tabbing away, preserving the single-surface promise of a CLI assistant.
  • Wary of scope creep: 'other live functionality' is open-ended enough to turn this into scaffolding a general agent platform instead of shipping the three asked-for things.
Yellow
Benefits
  • One chat turn can create a task, timebox it on the calendar, and pull a web fact — collapsing 3+ manual app-switches into one.
  • Notion page/DB creation lets Yoh spin up structure on demand instead of the user pre-building every container.
  • Live calendar write closes the loop the prior brainstorm left open — the daily plan becomes editable conversationally, not just re-rendered.
  • Web search turns Yoh into the front door for the existing Research Vault DB pattern — search-then-file becomes one flow.
  • Because chat-cli is already structured/deterministic, new capabilities can ship as small well-scoped commands rather than a fully open agent — safer and simpler to ship incrementally.
Black
Risks
  • Free-form Notion page/DB creation risks schema drift — a page whose properties don't match TaskDB's real fields becomes invisible to the planning engine.
  • Calendar write conflicts: an arbitrary-event-capable Yoh could collide with the Yoh Plan calendar's block-ID tracking or with real user-created events.
  • Web search results are non-deterministic and can be wrong or stale; without a cite/confirm step bad facts could quietly feed planning decisions.
  • Notion, Calendar, and search APIs all have quotas — per-turn live calls could hit throttling during high-usage moments like the morning ritual.
  • Moving chat-cli from deterministic parsing to a tool-calling LLM loop is an architecture shift with its own failure modes (hallucinated args, loops) not present today.
  • 'Other live functionality' left unscoped could balloon into new credential/OAuth surface area that wasn't budgeted for.
Green
New Ideas
  • Confirmation-gated writes: any create/destructive Notion or Calendar action gets a one-line confirm before executing, mirroring the existing 'propose, don't impose' rule.
  • A dry-run mode shows what would be created/changed without committing, building trust before write actions go live.
  • Scoped tool registry: expose a small fixed verb set (create_task, create_page_in, move_calendar_block, search_web) instead of raw API access.
  • Web search results get written into the Research Vault DB automatically when the user says 'save that,' reusing the existing DB instead of inventing a new store.
  • Time-blocking via chat ('push my 2pm to 4pm') maps onto the existing plan-block-ID tracking so edits stay reconciled with the Yoh Plan calendar.
  • A capability manifest surfaced in chat ('what can you do right now?') makes live functionality discoverable, not just known to the developer.
Blue
Process
  • Sequence by smallest gap first: Notion task/page writes, then calendar time-block editing, then web search last as the highest-uncertainty net-new piece.
  • Define a safety tier system (read-only / confirm-then-write / auto-write) up front that every new capability slots into, rather than deciding safety per feature ad hoc.
  • Decide early whether chat-cli stays a deterministic parser with more commands, or graduates to a real LLM tool-use loop — that fork point shapes everything downstream.
Technique 02 — Worst Possible Idea

Twelve wrong turns, twelve corrections

Every design flaw a live-write assistant could have — deliberately imagined at full strength — then flipped into the rule that prevents it. The flips, taken together, form most of the session's actual safety architecture.

⚠ Wrong turn

Give the chat CLI a raw Notion integration token with full workspace access and let the model run arbitrary API calls on the fly.

→
✓ Correct turn

Scope every write to an explicit, hardcoded verb set (a scoped tool registry) — never hand the model the raw token.

⚠ Wrong turn

Let Yoh auto-create and auto-schedule calendar events with zero confirmation, including moving or deleting the user's existing meetings.

→
✓ Correct turn

Writes are additive-only and confirm-gated by default; moving or deleting anything Yoh didn't create requires explicit named confirmation.

⚠ Wrong turn

Web search results get pasted straight into the plan or TaskDB as fact, with no indication they came from the web or when.

→
✓ Correct turn

Every search-derived write is tagged with source and timestamp so provenance is always visible later.

⚠ Wrong turn

One universal 'do_anything' tool takes a natural-language instruction and routes it internally to Notion/Calendar/search with no per-capability limits.

→
✓ Correct turn

Keep chat-cli's existing deterministic-parser strength — small, named, typed commands beat one mega-tool.

⚠ Wrong turn

New Notion pages get created with freeform titles/properties that don't match any existing DB schema, so the planning engine can't see them.

→
✓ Correct turn

Page/DB creation is always schema-validated against the target DB's real property names (e.g. DEFAULT_TASK_PROPERTY_NAMES) before writing.

⚠ Wrong turn

Calendar and Notion writes happen silently in the background with no chat transcript record, so the user has no idea what changed unless they open the app.

→
✓ Correct turn

Every live write is echoed back in chat as a one-line receipt (e.g. 'created task X, due Y').

⚠ Wrong turn

Web search runs on every single chat turn 'just in case,' burning API quota and slowing every reply.

→
✓ Correct turn

Search is a triggered capability (explicit ask or clear intent), never a default per-turn tool call.

⚠ Wrong turn

If a Notion or Calendar API call fails mid-action, Yoh just says 'done' anyway.

→
✓ Correct turn

Failures are surfaced honestly with a retry/undo path, never a false success.

⚠ Wrong turn

All new live capabilities ship at once in one giant PR with no staged rollout, so a bug in web search can take down task creation too.

→
✓ Correct turn

Ship capabilities independently, each behind its own safety tier, so one failing feature never blocks the others.

⚠ Wrong turn

The assistant uses its new write powers to 'proactively' reorganize the user's whole Notion workspace based on a hunch.

→
✓ Correct turn

Reinforces the existing 'propose, don't impose' rule from the prior Yoh session — even with write access, restructuring stays a proposal until confirmed.

⚠ Wrong turn

Hardcode API keys/tokens directly in chat-cli.ts source so the new live features are quick to wire up.

→
✓ Correct turn

Credentials load from env/config the same way the existing Notion/Calendar adapters already do — new capabilities follow the established adapter pattern, not a shortcut.

⚠ Wrong turn

Web search results are allowed to override or contradict decisions already logged in the memlog/plan without flagging the conflict.

→
✓ Correct turn

If a search result conflicts with existing plan data, Yoh surfaces the conflict rather than silently overwriting it.

Synthesis

What all three techniques were actually pointing at

Seven insights, surfaced independently across hats, flips, and the grid — then read together as one converging design.

Keystone insight

The safety-tier system (read-only / propose+confirm / auto-write+receipt) is the single most load-bearing idea in the session — it surfaced independently from Six Hats' Green/Blue hats, every Worst-Possible-Idea flip, and threads through nearly every Morphological combo. Design it once as a shared primitive, don't decide safety per-feature.

Scope discipline is the second recurring axis: auto-write is only safe when the target is Yoh-owned (Yoh Plan calendar, Yoh-created rows); anything touching the user's real calendar or full workspace needs propose+confirm regardless of trigger mode. Safety tier and scope are coupled, not independent.

Provenance (chat receipt + memlog log) is the antidote to nearly every Worst-Possible failure mode: silent background writes, swallowed API failures, unlabeled web-search facts. The fix in all three cases is the same move — never silent, always shown and logged.

The session converges against rebuilding chat-cli into an open LLM tool-calling loop. Instead: extend the existing adapter pattern (notion-adapter.ts, calendar-adapter.ts) with a small scoped tool registry of named, typed commands — the architecture fork resolves toward 'more commands,' not 'general agent.'

The most novel direction wasn't visible from any single technique alone: composing the two new capabilities together ('research X and file the results' — search then draft-page then confirm then create) is more valuable than either shipped in isolation.

Nearly every high-value idea reuses something that already exists rather than inventing new machinery: Research Vault DB as the search-results sink, Yoh Plan's block-ID tracking as the time-block edit anchor, the earlier session's 'propose, don't impose' rule as the write-confirmation philosophy, the existing data-completeness gate extended to also propose inferred values.
