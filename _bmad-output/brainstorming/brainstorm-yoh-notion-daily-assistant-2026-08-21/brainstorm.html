Technique 01 — Morphological Analysis

Seven dials, dialed in

Morphological analysis breaks a problem into independent parameters and picks a point on each spectrum. Reconstructed from the session, here is where each of Yoh's seven axes landed.

01Data scope

The Tasks DB has nine fields; only five earn their keep: Estimated Duration, Area, Due Date, Status, Energy. Projects DB stays an organizing folder, not a planning input. Research Vault is an on‑demand output store, not an input either. The daily plan is driven by the Tasks DB alone.

everything in Notion
Tasks DB alone
02Priority logic

Priority is never hand-set. It's derived: bigger/harder tasks and closer due dates rise automatically. A completeness gate keeps the input honest — Yoh proactively asks for missing due dates, durations, or energy ratings rather than silently guessing or letting a task rot unscored.

manual
derived
03
Plan granularity — the day's rhythm

The daily time budget is user-declared and can change by voice any time (2.5 hrs one week, 4 the next). Yoh may suggest raising it ahead of a known crunch, but never overrides it silently. Inside that budget, the default cadence is 70 minutes of work, 15 minutes of break, repeating — and a late correction made it literal: breaks are strictly clock-based, not aligned to task boundaries, even if that splits a task mid-stream. Break count simply scales with the budget (a 3‑hour budget earns 2 breaks).

strict clock
70 min work15 min breakrepeats to fill budget
04Memory model

Two layers: factual recall of what's actually been said, and a constantly-learning read on the user's behavioral patterns. Learned patterns are only ever proposed for confirmation, never silently acted on. Architecturally it's hybrid — a small "active" memory (recent days, current patterns, standing preferences) sits in front of every planning decision, while the full raw history lives cold, queried on demand and distilled into short pattern-statements rather than replayed in full.

stateless
full raw replay
05Hardware

A Raspberry Pi already on hand, a 3D-printed case, and a screen showing the web app — kept in the bedroom, away from water — with audio bridged over Bluetooth to a waterproof bathroom speaker. Idle, it falls back to a small, non-distracting red passive clock. A swiveling camera that nags about room messiness is flagged as a future, not immediate, ambition.

software only
dedicated ambient device
06Adjustment logic

A slipped task earns a small, capped priority bump the next day, stacking (still capped) with each consecutive slip. Blockers are handled as logistics only — Yoh reschedules around them, it doesn't try to solve them. Re-flow can happen mid-day in real time, but only when the user self-reports — Yoh never proactively pings mid-block.

fixed plan
reactive escalation
07Tone & personality

Default voice: a casual, peer-level secretary handing over a plan to execute, not a formal assistant. It sharpens to concise and educational for intellectual questions (deliberately avoiding "it's not just X, it's Y" as a crutch), and escalates toward authoritative/urging when the user is slipping. Fun voice packs (robot, Hulk, Morty…) are manual toggles only, fully decoupled from that tone escalation.

formal / static
casual + escalating
Technique 02 — Six Thinking Hats

Six hats, one honest look at the project

Structured rounds through facts, feeling, risk, value, ideas, and process — before any building started.

White · Facts

What's actually true

  • Hands-on experience with iOS/web/backend, a 3D printer, and a cloud/server setup already running — none of this is new ground.
  • Target: something useful by Sept 2, 2026 — about 12 days out.
  • Strictly solo: personal use, no co-builder, no other end users.
Red · Feeling

Cautious hope

  • This is attempt #2 — the first build of Yoh didn't work out.
  • The bet this time: running it through the BMad method produces a better outcome.
Black · Risks

What actually killed it last time

  • Not a build failure or a motivation failure — an efficacy problem. The features simply weren't useful in practice.
  • Named risks this time: too much friction (re-explaining context, instability/bugs, a personality mismatch, Yoh overstepping its scope) and bad plans — a schedule that's low quality or unrealistic.
Yellow · Value

What success looks like

  • One specific, trustworthy plan — if followed, every task and goal becomes completable.
  • Success is measured by whether the plan gets followed, never by feature count.
Green · Ideas

Three safeguards, invented on the spot

  • Every daily plan carries a one-line "why" (e.g. "leading with X — due soonest, biggest chunk") so a bad call is visible up front, not just in hindsight.
  • User feedback that a plan was bad gets written back into memory to improve future plans.
  • Yoh randomly asks the user to score its own output roughly every 4 days — a number plus a reason — and checks in more often if scores trend low.
Blue · Process

Keeping the session on track

  • Resolution: finish the planned technique batch — one invented technique, one facilitator-chosen — then converge and wrap.
Cross-technique insight

One mechanism, wearing four faces

These four rules surfaced separately, across different axes and different hats. Laid side by side, they're the same shape: hold steady while things are fine, escalate the moment the user is under strain.

The synthesis

Escalate under strain

Four independent decisions, one governing pattern — none of them designed together, all of them converging on the same response curve.

Slip-bump priority

slip 1slip 2cap

A slipped task gets a small, automatic bump each consecutive day it slips again — stacking, but hard-capped so a low-priority task can never leap to high priority from slipping alone.

Tone escalation

on trackslippingprocrastinating

Casual peer-secretary by default, shifting to more authoritative and urging exactly when the slip-bump mechanic detects the user is falling behind.

Night-ritual retry

check-in duenotificationspeaker call-out

Capped at two retries — phone notification, then a home speaker call-out — then Yoh stops and flags "you never checked in." Morning gets one push and moves on; night alone escalates.

Score-check frequency

baseline ~4dtrending lowmore frequent

Self-scoring starts on a loose ~4-day cadence at a random time, but tightens automatically the moment scores trend low, until things improve.

Technique 03 — Future Autopsy (invented)

Imagine it's already dead. Now write the report.

The invented technique: picture a specific future failure in detail, autopsy it, then invert every named cause into a safeguard built today.

CASE FILE — FEB 2027 (imagined) hypothetical
Cause of death — 1

The voice got annoying

Specifically: it said too much, sounded generically "AI-ey," and read as professional and corporate instead of cool — the opposite of the casual peer-secretary it was meant to be.

Cause of death — 2

Plans needed too much manual revision

The daily schedule stopped being trustworthy enough to just follow — the exact failure mode the whole project exists to avoid.

invert ↓ safeguard
Verdict

Existing safeguards were judged sufficient for cause 2 — no new gap found:

Why-reasoning on every plan Feedback writes back into memory Periodic self-scoring

Where the session closes the loop

Closing the loop

Five threads run underneath the whole plan. None of them respect the phase boundaries — they're what actually holds the six phases together.

P1P2P3P4P5P6
Escalate under strain
Propose, don't impose
Calendar: bridge, not home
Research Vault → Perplexity → browser
Periodic scoring

Escalate under strain and propose, don't impose aren't features of any one phase — they're load-bearing from Phase 1 onward, the same trust boundary that governs budget overrides, learned patterns, and blockers alike.

Calendar is introduced in Phase 1 purely as a stand-in for the app that doesn't exist yet, and recedes to passive history once the web app (P2) and iOS app (P4) take over.

Research Vault → Perplexity → hardware browser access is one feature that happens to land across two non-adjacent phases — the hardware-phase idea (P3) and the formally scheduled integration (P5).

Periodic scoring is the safeguard Future Autopsy singled out as sufficient — the mechanism specifically meant to catch an efficacy failure early this time.

Yoh is a Notion-driven daily planner built around one core loop — morning plan generation, then night close and adjust — governed by a single underlying escalate-under-strain mechanism and a propose-don't-impose trust boundary that guards against the exact scope-creep and annoyance risk named in the Black Hat and the Future Autopsy. The prior attempt failed on efficacy, not build quality — the periodic scored check-in is the safeguard specifically meant to catch that early this time.
