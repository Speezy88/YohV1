### Diff-scope review — cross-story boundaries (inline lenses)

**F4 — (6.4 → 6.5) Filing any search answer longer than 2,000 characters fails.**
- Source: `handleSaveSearchResultCommand` (`chat-cli.ts:1761`) passes the full `answer.answer` as `keyFindings`. `resolveCreatePageProperty` (`notion-adapter.ts:901–902`) writes it as a single `rich_text` text object with no chunking or truncation. Notion's API rejects a single `text.content` longer than 2,000 characters. `search-adapter.ts` sets no output-length limit on Perplexity (`body: { model, input: query }`), and Sonar answers with citations often run past that limit.
- Effect: `createPage` catches the rejection and returns `kind: "unreachable"` (`notion-adapter.ts:1023–1030`), so Spencer sees "I couldn't file that: …could not create…". Nothing is corrupted, but FR-29's main flow fails for long answers, and the error is labeled `unreachable` when it is really a validation failure.
- Verification: confirmed by reading the code. Not reproduced live (see Behavior verification).
- Disposition: **fix now.** Split `rich_text` values into ≤2,000-character segments inside `resolveCreatePageProperty` (Notion allows up to 100 segments). That also covers FR-26's `rich_text` fields. Add a test with a 5,000-character answer.
- Prevention: 6.5's plan checked schema names (6.1) but not the size limits of the upstream payload (6.4). Story plans that pipe one adapter's output into another's write should state the size limits.

**F5 — (6.4 → 6.5) "save that" can file an empty page or an older result.**
- Source: `handleSearchCommand` (`chat-cli.ts:1731`) returns `result.value` for an empty answer (`answer.length === 0 && citations.length === 0`). The caller then sets `lastSearchAnswer` (`chat-cli.ts:2198`), so "save that" files a page with a blank "Key Findings". When a search fails, `lastSearchAnswer` keeps the previous result, so "save that" files the old query. 6.5 AC3 says "there must be an actual search result in play."
- Disposition: **fix now (small).** Don't set `lastSearchAnswer` for an empty answer. Clear it when a search fails.

**F6 — (6.3 ↔ 6.5, via `8a35729`) The looser Notion write trigger takes over natural "save" phrasings.**
- Source: `parseCreateItemCommand` runs before `isSaveSearchResultCommand` (`chat-cli.ts:2150` vs `:2163`). `NOTION_WRITE_VERB_RE` includes `save`/`file` (`chat-cli.ts:1592`), and `NOTION_DB_MENTION_RE` matches "…notion…research vault…". "save that to my notion research vault" therefore goes to the FR-26 *drafting* path, which asks Claude to draft fields from the literal request text instead of the search answer. `SAVE_SEARCH_RESULT_RE` (`:1628`) only accepts "to the (research) vault" with no "notion". This trigger was added in the post-story fix `8a35729`, after 6.5 shipped, and no test covers the interaction.
- Effect: confirm-gated, so nothing is written without a "yes", but the draft will not contain the search result.
- Disposition: **fix now (small).** Check the save-search trigger before the create-item trigger when `lastSearchAnswer` is set, or widen `SAVE_SEARCH_RESULT_RE` to accept "…notion research vault". Add a test for that exact phrase.

**F7 — Confirm-prompt handling differs between the three FR-26/FR-27/FR-25 gates.**
- Source: FR-27 (`chat-cli.ts:1930–1946`, reprompt at `:1939`) asks again when the reply isn't yes/no ("Please answer 'yes' or 'no'"). FR-26 (`:1699–1707`) and FR-25 (`:505–520`) treat any reply that isn't "yes", such as "yep sure" or "y", as **no**.
- Disposition: **accept.** Both behaviors fail safe. Worth unifying the next time these handlers are touched.
