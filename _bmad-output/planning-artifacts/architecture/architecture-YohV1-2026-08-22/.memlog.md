- (constraint) Superpowers task-shape contract (governs how the spine's boundaries must decompose downstream): (1) tasks must be mostly independent -- no two tasks mutate the same file or share mutable internal state; genuine tight coupling is flagged, not artificially split, since Superpowers routes coupled work differently; (2) inter-task dependencies are expressed as explicit interface contracts -- concrete function/API signatures (Superpowers' own Consumes/Produces framing) -- never prose behavior descriptions; (3) each task sized to one clean TDD unit -- one behavior, one failing-test-then-implementation cycle; (4) each task's context is self-contained (full task text handed to a subagent with no other files open) -- avoid heavy cross-referencing between tasks/sections; (5) file-level ownership per task -- explicit Create/Modify/Test file paths, not shared modules multiple tasks incrementally touch.
- (direction) Implication for this spine: module/file boundaries must be cut fine-grained enough (one capability/behavior per file) that ownership is unambiguous per future task, state mutation must be avoidable across boundaries (favors a pure-core/thin-adapter paradigm over shared mutable service objects), and every boundary crossing must be documented as an explicit typed signature (Consumes/Produces) rather than prose -- this drives the Design Paradigm and Consistency Conventions choices.
- (decision) Paradigm: Functional Core / Imperative Shell. Pure, stateless domain functions (one behavior per file: Derived Priority, Slip-Bump, Time-Budget fit, Work/Break fitting, Data-Completeness Gate, Escalate-Under-Strain) with zero side effects; thin imperative shell (adapters + ritual orchestration) handles all I/O. Plain typed function signatures are the boundary contract -- no formal ports/DI layer, chosen over Hexagonal to avoid ceremony not needed for a single permanent user.
- (decision) Language/runtime: TypeScript on Node.js. Official SDKs exist for both integrations (Notion, Calendar); static types make Consumes/Produces boundaries compiler-checked, directly reinforcing the Superpowers contract discipline.
- (version) Verified 2026-08-22 via web search: Node.js 24 is the current active LTS (support through Apr 2028); Node 24.12.0+ ships STABLE native TypeScript type-stripping (run .ts directly, no tsc/ts-node/build step -- type stripping only, not type-checking, so tsc --noEmit remains a separate verification step). TypeScript 7.0.2 is current GA (Go-native compiler rewrite, ~10x faster than 6.x, released 2026-08-05). @notionhq/client (notion-sdk-js) latest v5.22.0 -- official Notion JS SDK. googleapis npm package latest v175.0.0 -- official Google API Node client, covers Calendar v3.
- (decision) Storage: better-sqlite3 over node:sqlite. node:sqlite is Release Candidate (Stability 1.2) on Node 24, not yet final; better-sqlite3 has years of production hardening and is the safer pick against a hard Sept 2 2026 deadline. Single-file embedded DB matches the 'infra Spencer already owns' constraint (no server, no new paid service).
- (decision) Test runner: built-in node:test + node:assert (stable since Node 20, production-quality by 2026). No external test framework dependency -- matches minimal-ceremony paradigm and gives each Superpowers task a self-contained one-file-in/one-test-file-out TDD unit.
- (decision) Scheduling: OS-scheduled one-shot commands. cron/systemd-timer/launchd invokes 'yoh ritual morning' / 'yoh ritual night' as one-shot processes that run and exit; a separate 'yoh chat' command starts an on-demand REPL for Mid-Day Re-Flow/Blocker reports/Time Budget changes. Both entry points call the same core+adapters. Rejected long-running daemon: avoids Yoh owning uptime/crash-recovery/restart-on-boot itself when the OS already provides scheduling infra Spencer has.
- (decision) Push notification transport: Pushover. One-time per-platform license, single HTTPS POST per notification, used for FR-1 Morning Plan delivery and FR-13's first (push) escalation attempt.
- (decision) Calendar write target: dedicated secondary 'Yoh Plan' Google Calendar, resolving PRD Open Question #3. Ownership guaranteed by construction (every event on it is Yoh's) rather than a runtime tag-check -- satisfies the PRD's harder-than-usual data-integrity NFR structurally. Enables narrower OAuth scoping: calendar.app.created-equivalent write scope on the secondary calendar, read-only scope on the primary (FR-21 only ever reads primary, never writes it). Spencer views both calendars overlaid natively in Google Calendar.
