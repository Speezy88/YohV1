# Review: Epic 13 architecture decisions AD-25..AD-31

Spine line refs are ARCHITECTURE-SPINE.md. Code refs are under src/.

1. **critical / AD-30** - Neither PatternKind can be computed from stored data. `area-overrun` needs "completion time minus planned block start", but `completions` stores only task/area/due/estimate/completed_at/source (adapters/completion-log.ts:58-67), with no block start. The only place block starts live is `plan_calendar_snapshot` (adapters/plan-calendar-snapshot-store.ts:26-35), which holds the last-written layout per date, not the morning plan. `completed_at` is also the tick time, and for `source='close-out'` it is the ritual time. `area-slips` cannot use slip history: it keeps only `consecutiveSlipCount` + `lastSlipDate` and is cleared on completion (adapters/memory-store.ts:849-853, 917). That cannot give "4 occurrences spanning 14 of the last 42 days". Fix: add a `planned_start`/`planned_end` snapshot column to `completions` (filled at check-off from the snapshot) and an append-only slip-event log, exclude close-out rows from overrun, or drop the kinds to what is stored.
2. **high / AD-26, AD-27** - "Forgot: {text} - Undo" (UX Remembered Receipt) and FR-54 both promise Undo, but AD-26 says forget/Delete "removes the whole chain" and gives no tombstone. Undo is defined only for filings. Fix: soft-delete (`status='deleted'`, purged on the next user turn or by a sweep) so Undo can restore, and state that FR-59 Memory-page deletes are hard deletes.
3. **high / AD-27, AD-29** - Nothing decides that a stated Planning-preference "maps to a real scheduler setting", nor who parses "2:30" into a `RuleSettingKey` + value. Nothing says who creates the `Proposal<RuleChange>` or in which tx (filing tx? after receipt?). `validateFiling` lists no rule-mapping step. Related gaps: Undo of the filing must withdraw the pending Proposal; a restate of a `declined` item must not re-propose (FR-57 "not proposed again unless Spencer raises it again"), and AD-26 never says what `rule_change` a new version inherits. Fix: add a `core/planning-settings.ts` `mapPreferenceToRuleChange(extracted)` step (LLM proposes key/value, core validates against the closed union), created in the filing tx, with explicit rules for Undo and superseded/declined versions.
4. **high / AD-29** - `defaultTimeBudget` collides with the existing Time Budget, which lives in memory-store as `TIME_BUDGET_ID` with its own proposal path (core/time-budget.ts:306-338; memory-store TIME_BUDGET_ID). This creates two owners of one value. Fix: drop it from `RuleSettingKey` and route FR-57 Time Budget conflicts through the existing time-budget proposal, or migrate it explicitly.
5. **medium / AD-29** - "resolvePlanningSettings is the scheduler's only settings input" is not enforceable. `WORK_START_TIMES` is read directly inside core/school-day.ts (`workStartMs`, line 76), and the protected windows are a constant array (school-day.ts ~:60). Every caller (morning-ritual, reshuffle, mid-day-reflow, routine-placement, plan-edit) needs a signature change. Fix: name the functions that must take a `PlanningSettings` parameter, and add a layering/source-scan test forbidding direct use of the defaults outside `resolvePlanningSettings`.
6. **high / AD-27, AD-31** - The SSE contract is underspecified, so two builders will diverge. AD-27 says `done`, then `remembered`, "then the stream closes". AD-31 adds `rating` after the receipt. UX also puts a rule-change Proposal card after the receipt and a Pattern card elsewhere. The existing union has only status/delta/done (types/api.ts:424-426). Missing: event names and payloads, order (`remembered` -> `proposal` -> `rating`), whether `done` carries `ChatTurnResponse`, and how one receipt line carries 2 items + folder + Feedback scope + expiry + an Undo token. Fix: add a single `ChatStreamEvent` type to AD-27 with those payloads and the fixed order.
7. **medium / AD-27** - The explicit-command path is undefined. `/remember` must pick a folder and check restate/contradiction, but the only folder/dedupe logic is the Haiku `extractMemories` call ("Otherwise ..."). Also undefined: "forget" with several matches (FR-55 Structured Question, one-shot per turn, needs a resumable flow like AD-16), what "last one filed" means (needs stored pointer), and that "What was off?" answers go through the same folder-forced-to-Feedback path. Fix: state that commands call `extractMemories` with a forced-`stated` flag (and a forced folder for Rating), and add the forget-disambiguation as a stored interaction request.
8. **medium / AD-26, AD-28** - Memory-page semantics have no home. (a) "Keep as history" for an expired/needs-review item has no state (`status` is only current|superseded), so it stays in Needs review forever. (b) "Merge on duplicate edit" (FR-59) is absent. (c) "Items not loaded are marked" - AD-28 says overflow "appears in Needs review" but the overflow is computed by a cap, so the page needs the same `MemoryContext` selector output. (d) FR-56/59 say "unused or unconfirmed for 120 days"; AD counts only `confirmed_at` and nothing records "used". (e) "newest first" is ambiguous (created vs confirmed). Fix: add `status='history'`, a merge action (new row superseding both), and one `core/` selector shared by recall and the page.
9. **medium / AD-25, AD-26, AD-28** - Degradation is not stated. FR-52/54/56 require Chat to still answer when the chat or memory store is down, with no success receipt. AD-25 stores Spencer's turn "before the model call" and AD-28 loads memory in the request path, with no fallback. Fix: add one sentence per store: read/write failure is caught, logged, the turn proceeds without it, and no `remembered` event is sent.
10. **medium / AD-30** - Pattern lifecycle is incomplete. (a) Where pending Proposals sit across days (UX: also at top of the Patterns folder) and how nightly detection avoids re-creating one already pending. (b) The 30-day quiet period is "keyed by (kind, Area)" but nowhere stored; AD-3 proposals are presumably deleted on resolution. (c) `areaDurationPadding` value derivation (median overrun? rounded?) is unspecified. (d) FR-58 requires the reasoning line to cite a confirmed pattern when it affects a placement; core/plan-reasoning.ts is not listed. Fix: add a `pattern_state` row per (kind, Area) with pending/declined_at, define the padding formula in `pattern-detect.ts`, and add plan-reasoning to the map.
11. **medium / AD-31** - The Rating rules do not match the UX/PRD. Unspecified: how "sending another message" records a dismissal (client call to `POST /api/rating {dismissed}`?), what counts as substantive (needs a flag on `ChatTurnResponse` set by `app/`, not inferred by the web), reset of consecutive dismissals on an answer, the 1-week pause, and that `extra_prompt_due` is capped at one per day. "Randomized turn" needs a defined draw point. Fix: list the endpoint payloads and the pure function's inputs/outputs in AD-31.
12. **medium / AD-31** - The Self-Check retirement list is narrower than the code. Self-check also appears in rituals/morning-ritual.ts, rituals/ritual-shared.ts, core/open-item-questions.ts, core/open-item-answers.ts, core/escalate-under-strain.ts, core/error-copy.ts, app/surface-open-items.ts, app/answer-open-item.ts, shell/server.ts, shell/ritual-cli/self-check-deps.ts, adapters/memory-store.ts, types/domain.ts, and web ChatPanel/chatStore. Fix: replace the list with "remove every self-check reference; grep must be empty" and say whether Escalate-Under-Strain still reads Self-Check scores (FR-60 says a 1 shortens the interval for Rating).
13. **medium / AD-28** - Layering and type-level claims. `core/memory-context.ts` "FTS5 bm25 top 5" is a DB query, so it belongs in the adapter, with core only selecting/formatting. "Capture" receiving memory is ambiguous, because `classifyCapture` sits before `classifyChatIntent` in routing (chat-turn) and AD-28 says classification takes none. Nothing states FR-56's "no memory item can weaken or skip a confirmation". Fix: split the adapter query from the pure builder, name `classifyCapture` as memory-free (or split its create-item step), and state that `confirm-proposal.ts` and the tier logic never read memory.
14. **low / AD-25** - Moving history server-side changes an existing wire contract: `ChatTurnRequest.history` and `isChatHistory` validation in shell/server.ts:1225-1235, `trimHistory` pairing logic in app/chat-turn.ts:203-206, and the fixture server. Also unstated is what is stored if the client aborts mid-stream (partial Yoh turn?). Fix: list these as required edits and store partial text with a `truncated` flag.
15. **low / AD-26, AD-27** - `expires_on` at filing (who chooses it: Haiku output validated by core?), the maximum item text length (the 60-item cap does not bound prompt size), and `MEMORY_FILING_TIMEOUT_MS` value are unset. Fix: add an item-length limit and state that the expiry comes from `extractMemories` and is validated by `validateFiling`.

Verified OK: `WORK_START_TIMES` exists as claimed (core/school-day.ts:70); the stable/volatile cache-block split exists (adapters/llm-adapter.ts:176-182, 652); `MAX_CHAT_HISTORY_TURNS` is an app constant (chat-turn.ts:96); backup-cli copies the whole SQLite file via `db.backup` (backup-cli.ts:49), so new tables are covered; rituals do not import `app/`; the Pattern proposal path (night-ritual -> Proposal -> confirm-proposal) respects layering.
