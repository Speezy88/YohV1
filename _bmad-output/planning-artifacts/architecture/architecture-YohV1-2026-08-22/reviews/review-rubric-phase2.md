# Verdict

**NOT CLEAN.** Two critical findings (one a direct type-level contradiction of live, heavily-used
brownfield code; one a false "moved, never copied" claim about the CLI-retirement mechanism that
undermines FR-42/FR-48/FR-50's central integrity guarantee), plus high/medium gaps in storage-shape
specification, test strategy, and two cross-process "tuning number" contracts that are actually
divergence points AD-6 already taught this spine how to prevent. The rest of the Phase 2 amendment
is coherent, well cross-referenced, and honestly self-critical (e.g. the trash-on-completion
reversion is correctly tracked as a needed migration story). None of the findings below require
re-litigating a Spencer-owned business decision — they are architecture-level fixes.

## Findings

### CRITICAL — AD-24's new `PlanBlock.kind` union silently drops `"calendar-anchor"`, contradicting live code and FR-33
- **Location:** ARCHITECTURE-SPINE.md, AD-24 Rule ("`PlanBlock` gains `kind: 'work' | 'break' | 'routine'` … in `types/domain.ts`"); also Structural Seed `types/domain.ts` comment.
- **Evidence:** `src/types/domain.ts:318` currently defines `export type PlanBlockKind = "work" | "break" | "calendar-anchor";` and the doc comment explicitly defines `calendar-anchor` as "a fixed Google Calendar event the Plan is built around, not a block Yoh can reschedule (FR-1)." This value is load-bearing in at least four existing files: `src/core/work-break-fit.ts` (places every non-Yoh `CalendarEvent` as an immovable `calendar-anchor` block), `src/rituals/mid-day-reflow.ts` (`.filter((b) => b.kind !== "calendar-anchor")` — twice — to keep non-Yoh events un-reschedulable), `src/adapters/calendar-adapter.ts`, and `src/shell/ritual-cli.ts`. FR-33 (Phase 2) *requires* this exact concept to keep working during a reshuffle ("a reshuffle never moves, resizes, or deletes a Calendar event Yoh did not create. Those events are fixed anchors, exactly as in FR-1").
- **Why it's a real divergence risk:** AD-24 is the kind of AD a subagent implementing Routines would follow literally — it states the *complete* new union, not a delta. A task built from AD-24's Rule text alone would either (a) fail to compile against every existing anchor-handling call site, forcing an ad-hoc fix improvised mid-task, or (b) "fix" the type by re-adding `calendar-anchor` in a way another concurrently-dispatched reshuffle task doesn't expect. This is exactly the "two AD-compliant-but-incompatible units" failure mode AD-6/AD-9 exist to prevent, reproduced here by the Phase 2 amendment itself.
- **Fix:** Change AD-24's Rule to read `kind: 'work' | 'break' | 'calendar-anchor' | 'routine'` (extends, never replaces, the existing union), and add one clause noting Routine Blocks are a new *addressable* kind alongside the untouched `calendar-anchor` kind FR-33 still depends on.

### CRITICAL — AD-16's "moved, never copied" claim is false for chat-cli.ts's blocking multi-turn handlers; no redesign is named
- **Location:** ARCHITECTURE-SPINE.md AD-16 Rule ("`chat-cli.ts`'s existing logic is **moved** into `app/`, never copied... Shells contain transport only") and AD-3's "read it as 'the `app/` function calls/extracts'" gloss; memlog line 63 ("migrates INTO app/ (moved, never copied), so FR-48 surface-agnostic confirmation is structural").
- **Evidence:** `src/shell/chat-cli.ts`'s `ChatCliIo.readLine` is documented to "wait indefinitely" for one line of terminal input and never time out (line ~259-260). Handler functions such as `answerDataCompletenessRequest` (line 476), `answerSelfCheckRequest`, `answerNightCloseOutRequest`, and `answerProposalRequest` each run an interior loop that calls `io.readLine()` multiple times *within a single function invocation* — asking one field, blocking for the answer, validating, re-prompting on a bad answer, moving to the next field — a genuinely stateful, multi-round synchronous conversation embedded in one call. `app/`'s prescribed shape, per AD-16 itself, is `(deps, input) → Promise<Result<Output, YohError>>` — a single-shot request/response function an HTTP handler calls once per POST. An HTTP request handler structurally cannot "wait indefinitely" mid-request for the next chat message, which will arrive as a *separate* POST.
- **Why it's load-bearing:** This is the mechanism FR-42 (Chat parity), FR-48 (surface-agnostic confirmation), and FR-50 (CLK retirement) all depend on being sound. As written, a subagent tasked with "move `answerDataCompletenessRequest` into `app/`" has no guidance on how to turn a blocking multi-question loop into a resumable state machine (persisting "which field is currently being asked" as durable state between HTTP turns, e.g. as part of the existing `InteractionRequest` record) — and a separately-dispatched task building `shell/server.ts`'s chat-turn endpoint would have to independently invent the same resumption contract. Two independent inventions of "how does a paused multi-field prompt resume across HTTP requests" is precisely the kind of undocumented shared contract this spine otherwise pins explicitly (cf. AD-6's `computeEscalation`, AD-13's `resolveCalendarEditRoute`).
- **Fix:** Add an explicit AD-16 (or new) clause: functions with an interior multi-turn loop are *restructured*, not moved verbatim — each becomes "ask the next unanswered field/question, given what's already answered," driven by state persisted on the `InteractionRequest`/`Proposal` record itself (not function-local loop state), so one HTTP POST = one question-answer step. Name this explicitly for `answerDataCompletenessRequest`, `answerSelfCheckRequest`, `answerNightCloseOutRequest`, and `answerProposalRequest` (or whichever survive), since these are the four places brownfield code proves the "straight move" claim doesn't hold.

### HIGH — Storage shape for the five new Phase 2 owner files is unspecified; the outbox and job-runner need semantics the existing generic table can't cleanly give
- **Location:** AD-10 Phase 2 bullet ("New durable data gets new owner files... Each record kind has exactly one owning file"); AD-18 (outbox: `{seq (monotonic), topic, entityId}`, "server tails the outbox"); AD-21 ("a runner... claims jobs one at a time").
- **Evidence:** The only existing storage primitive, `memory-store.ts`, is a single generic `records` table keyed by `(kind, id)` storing each entity as a JSON blob (`src/adapters/memory-store.ts:145-160`), upserted by id — its own doc comment explicitly anticipates but does not mandate "a later task adding its own dedicated tables." AD-10's Phase 2 bullet never says whether `completion-log.ts`, `notification-store.ts`, `job-store.ts`, `plan-state-store.ts`, and `routine-store.ts` (a) reuse this generic `(kind,id)` blob table under new `kind` strings, each opening its own `better-sqlite3` connection to the same file, or (b) each define their own dedicated SQL table(s) with their own `initSchema`-equivalent. Neither AD-18's monotonic-`seq` append-and-tail outbox nor AD-21's atomic "claim one job" runner is achievable cleanly on an upsert-by-id JSON blob table (no autoincrement sequence to tail from, no indexed `status` column to claim against). Desk metrics (AD-23, `core/desk-metrics.ts` over completion-log rows) and the streak/heatmap likewise want real queryable columns, not blob scans.
- **Why it's a real divergence risk:** Five files, plausibly five different subagent tasks, each need to decide "what SQL do I actually run" with no shared answer given. Whoever builds the outbox and whoever builds `job-store.ts`'s claim query will independently invent incompatible schema conventions (dedicated tables vs. generic blobs, one connection vs. many) unless the spine picks one.
- **Fix:** Add a short AD-10 (or new) rule: each new owner file constructs its own dedicated SQL table(s) via its own schema-init function, using its own `better-sqlite3` connection to the same file path (safe under WAL, per AD-10's existing "share one SQLite file" framing) — the generic `records` table stays `memory-store.ts`'s own, not a shared primitive. Name the outbox table's actual columns (an `INTEGER PRIMARY KEY AUTOINCREMENT` `seq`) and the jobs table's claim mechanism (e.g. a single `UPDATE ... WHERE status='queued' ... RETURNING` or equivalent) so two tasks don't invent two different locking strategies.

### HIGH — No testing strategy is specified for `app/`, `shell/server.ts`, or `web/`
- **Location:** Whole spine — Stack table only lists `node:test / node:assert` (line 293), with no Phase 2 amendment anywhere naming how `web/` (a Vite + React SPA) gets tested. Checked: zero mentions of `vitest`, `testing-library`, `playwright`, `jsdom`, or any client test tool in the file.
- **Evidence:** `package.json`'s only test script is `"test": "node --test"` — Node's built-in runner, which has no DOM and cannot render a React component or simulate a drag gesture (FR-30/FR-31's core interaction). The project's own Superpowers task-shape contract (memlog frontmatter, `.memlog.md` line 10-11) requires "each task sized to one clean TDD unit — one behavior, one failing-test-then-implementation cycle," which is meaningless for `web/` tasks without a chosen client test tool. `server.ts`/`app/*` can plausibly extend `node:test` (they're plain Node/Hono code), but that's never stated either — currently a reader must infer it.
- **Fix:** Add one Stack-table row (or a Testing convention row) naming: (1) `app/*` and `shell/server.ts` continue on `node:test`/`node:assert`, consistent with existing convention; (2) a client test tool for `web/` (e.g. Vitest + React Testing Library, given Vite is already the bundler) and whether FR-30/FR-31's drag interaction gets any automated coverage at all or is explicitly deferred to manual verification. Silence here is itself a decision, but it should be a stated one, not an omission a reviewer has to surface.

### MEDIUM — Two "tuning numbers" left in Deferred are actually cross-process/cross-file contracts, not single-file constants
- **Location:** Deferred, "Tuning numbers" bullet (line 458): "heartbeat interval and staleness threshold (AD-7)" and "undo window (~5 s, AD-20)."
- **Evidence:** The heartbeat interval is *written* by `server.ts` (AD-7 Phase 2 bullet) and *checked* by `ritual-cli.ts morning` in a separate process — if these two independently-built pieces pick the interval/threshold pair independently, `ritual-cli.ts` will either false-positive-alert every morning (threshold tighter than the write interval allows) or fail to detect a genuinely dead server (threshold too loose). The undo window (AD-20, `plan-state-store.ts`'s `commitAt = now + undo window`) is also rendered client-side as a countdown/animation (FR-46's "motion accompanies state" + FR-41's undo UX) — a second, independently-built consumer (`web/`) that must agree on the same number, ideally without hardcoding it twice.
- **Why it matters:** This is the exact failure class AD-6 was written to prevent for `computeEscalation` (a shared value two callers might otherwise independently re-derive) — the spine already knows how to fix this, it just didn't apply the same treatment here.
- **Fix:** Pin both as named, single-sourced values (e.g. exported constants in `types/domain.ts` or a small shared config module `app/` and `web/` both import/receive over the API), not merely parallel "Deferred: pick a number" bullets each future task could independently decide.

### MEDIUM — NFR-Accessibility's contrast standard is bound but never stated or carried into Deferred, despite the PRD flagging it as an open risk
- **Location:** Frontmatter `binds: NFR-Accessibility`; AD-17 Binds; Consistency Conventions "Web UI" row (only covers motion/reduced-motion and fonts, not contrast).
- **Evidence:** PRD FR-46 explicitly requires "Contrast meets the Accessibility NFR (§6) — neumorphism's low-contrast default does not ship unchecked," and PRD Open Question #9 names this as an unresolved design risk ("whether off-white + neumorphism clears [WCAG]... is a design task"), and PRD §12 lists "WCAG 2.2 AA as the contrast standard" as an unconfirmed inline assumption. The spine binds NFR-Accessibility to AD-17 and the Web UI convention row, but never states a concrete standard (WCAG 2.2 AA or otherwise) and never carries the neumorphism-contrast risk into its own Deferred section — unlike the OAuth production-mode item, which the spine deliberately gives prominence to as a named build gate.
- **Fix:** Add one Deferred bullet naming the contrast standard (or explicitly deferring it to `bmad-ux`'s token values) as a build gate on shipping any neumorphic surface — mirroring how the OAuth item is elevated rather than left as a bare cross-reference.

### LOW — Migration of `chat-cli.ts`'s 2,844-line test file is unaddressed
- **Location:** AD-16 Rule / FR-50 Structural Seed note ("`chat-cli.ts` is deleted once FR-42's parity list passes... Deleting it removes no logic, because the logic already lives in `app/`").
- **Evidence:** `tests/chat-cli.test.ts` is 2,844 lines, presumably exercising the very handler functions AD-16 says move into `app/`. The spine states the *logic's* migration path but never mentions the *tests'* migration path — whether they move file-for-file into `app/*.test.ts`, get rewritten against the new resumable-state-machine shape (see the CRITICAL finding above), or risk silently being dropped when `chat-cli.ts` is deleted.
- **Fix:** Add a sentence to AD-16 or the Deferred "Shipped-epic behavior changes that need Phase 2 stories" bullet naming that each moved `app/` use-case's existing CLI-side test coverage moves and is rewritten with it, under the same file-ownership rule (AD-9) as the code itself.
