# Reconciliation Pass — PRD Phase 1.5 vs Architecture Spine

Phase 1 (FR-1–FR-24) was already reconciled in an earlier pass and is not re-litigated here. This pass covers only the new Phase 1.5 material.

## 1. Testable consequences without a concrete architectural home

Most FR-25–FR-29 consequences map cleanly onto a spine rule:

- FR-25 → AD-3 (Proposal<T>), AD-11 (revised, confirmed value flows through existing `updateTaskFields`), fallback-to-plain-ask preserved.
- FR-26 → AD-3 (Proposal<T> for the draft/confirm step), AD-12 (schema validation at draft-time and write-time, closed `database` enum).
- FR-27 → AD-13 (confirm-gated exception, no-delete type-level guarantee).
- FR-28 → AD-14 (search-adapter.ts, structurally no write import).
- FR-29 → AD-12 (`createPage(database: 'ResearchVault', …)`), AD-14 (search leg).

**Gap found — chat receipts have no architectural home.** FR-26's consequence ("A successful creation is echoed back in chat as a one-line receipt naming the item and its database"), FR-27's consequence ("A successful edit is echoed back in chat as a one-line receipt naming the event and the change made"), and the NFR-DataIntegrity text itself ("Every write triggered from Chat (FR-24–FR-29) is echoed back to Spencer as a one-line receipt in that same chat") are never mentioned anywhere in `ARCHITECTURE-SPINE.md` — confirmed by a direct grep for "receipt" against the spine file, zero matches. The PRD addendum *does* cover this ("Provenance/receipt mechanism… a chat-cli output concern only, no new storage"), but that reasoning was never carried into the spine itself — no AD rule, no Structural Seed comment, no Capability Map entry assigns this behavior a home. `chat-cli.ts` is the obvious place it would live given AD-3/AD-5's existing confirm-flow ownership, but the spine doesn't say so. Minor severity (the fix is almost certainly "one sentence in AD-3 or AD-12"), but it is a genuine documentation gap in a testable requirement, not a nitpick.

**Soft gap — FR-28's "surfaced honestly, never a confident answer" on search failure.** AD-8's `YohError.kind` enumeration (`missing-field`, `auth-expired`, `unreachable`, `rate-limited`, `validation`, `stale-proposal`, `conflict`) has no kind cleanly covering "provider returned zero results" as distinct from a hard failure — `search-adapter.ts` presumably throws and `unreachable`/`rate-limited` catch the outage case, but a legitimate no-results response isn't a thrown error at all, it's a valid response the LLM must not dress up as confident. This is arguably more a prompt-behavior concern than an architectural one, but the spine gives it zero structural backstop (contrast with AD-13's type-level delete prevention). Worth a one-line addition to AD-14 if it matters in practice.

## 2. Contradictions with PRD Non-Goals (§8) / NFRs (§6)

- **FR-27's "never delete a non-Yoh event" Non-Goal — honored, and enforced structurally, not just by convention.** AD-13's `CalendarEditChange` union has `move | resize | create` variants only, with no `delete` variant — the spine states plainly "it isn't a value the type system can construct here, not merely a rule someone has to remember." This is a real type-level guarantee, not a documentation promise. Confirmed clean.

- **"No raw Notion/Calendar API access routed from freeform chat text" Non-Goal — honored.** AD-12 keeps `notion-adapter.ts`'s write surface a closed enumerated set (`setTaskStatus`, `updateTaskFields`, `createPage`) called only from `chat-cli.ts`; AD-13 adds only the named `proposeCalendarEdit`/`applyCalendarEdit` pair; AD-14's `search-adapter.ts` holds no write capability at all, structurally (no import path to a write function). AD-10 keeps the one `OAuth2Client` instance held solely by `token-store.ts`, never exposed to `llm-adapter.ts`. Confirmed clean — chat intent routing (`llm-adapter.ts`) only ever calls these named functions, never a raw client.

- **"No search on every chat turn" Non-Goal — describes intent more than it structurally prevents it; real gap worth flagging.** AD-14's only enforcement mechanism is classification: "one more intent category in `llm-adapter.ts`'s existing chat-intent-routing responsibility," i.e., an LLM call deciding whether a given message is search-worthy. Unlike AD-13's delete-prevention (a type the compiler can't construct), there is no structural or rate-limiting backstop here — nothing stops a misclassification from firing a paid Perplexity call. The one architectural safeguard that *would* function as a hard backstop — a daily call cap — exists only as a **Deferred** item ("pick... a daily call cap Spencer is warned about rather than silently throttled by"), not an ADOPTED rule, and even that stated design ("warned about," not throttled) is explicitly non-blocking by intent: it informs after the fact rather than preventing an over-trigger. So as currently ADOPTED, the Non-Goal is protected by prompt/classification correctness alone. This is consistent with the PRD's own framing (FR-28's classification boundary is itself deferred to the addendum, "start narrow… widen only if under-triggering turns out to be the actual problem"), so it isn't a spine-introduced defect — but the spine also doesn't flag the absence of a structural backstop as a residual risk the way it does elsewhere (e.g., AD-7's "Total-outage detection gap" is explicitly named as a known limitation). Worth adding a similar explicit caveat under AD-14 or Deferred.

## 3. AD-13's OAuth-scope-widening [ASSUMPTION] vs PRD/addendum

The PRD/addendum never discuss Calendar OAuth scopes at all for FR-27 — that's expected, since scope shape is architecture-level detail and Open Question §11 item 3 (primary calendar + tagging vs. dedicated secondary calendar) was left open specifically for architecture to resolve. AD-4 resolved that question with its own judgment call (dedicated "Yoh Plan" secondary calendar, primary read-only), explicitly flagged as "this run's judgment call, not something the research itself settled." AD-13's need to widen the primary-calendar grant to read/write is a **second-order consequence of AD-4's own earlier choice**, not something inherent to FR-27's PRD text — so the PRD "not anticipating" it is expected and not a problem in itself. The spine correctly tags it `[ASSUMPTION]` and folds it into the existing Deferred item on exact 2026 Calendar OAuth scope names, with an owner and revisit point. Procedurally, this is handled well.

**However, a sharper problem falls out of combining AD-4, AD-10, and AD-13 that the spine does not currently resolve.** AD-4's own defense is: "Read access to the primary and write access to 'Yoh Plan' use separate OAuth scopes, so a coding mistake that tried to write the primary fails at the API layer, not just at review." AD-4's Phase 1.5 note asserts this guarantee "is unchanged for the automatic path it governs" after AD-13 lands. But AD-10 establishes `token-store.ts` as the **sole constructor and holder of the `OAuth2Client`** — i.e., one shared client, one shared scope grant, used by both the AD-4 automatic path and the AD-13 confirm-gated path (both live in `calendar-adapter.ts`). If AD-13 widens *that same client's* grant to read/write on the primary calendar, then the automatic path's defense-in-depth claim — "fails at the API layer, not just at review" — is no longer literally true: after the widening, a coding bug in the automatic path that mistakenly targeted a primary-calendar event would now *succeed* at the API layer, because the credential itself can write there. The only thing preventing it becomes the ownership-tag check in code (i.e., "review," the exact backstop AD-4 says it doesn't want to rely on), not the OAuth scope. AD-4's Phase 1.5 note's claim of an "unchanged" guarantee is therefore inaccurate as written, given AD-10's single-client design — either AD-10 needs to be revised to support two separately-scoped OAuth clients (one read-only-primary for the automatic path, one read/write-primary for AD-13's path), or AD-4/AD-13 need to acknowledge that the automatic path's API-layer defense is weakened once the shared grant widens. This is the most concrete, actionable finding from this pass.

## 4. Safety-tier framing (PRD §6) vs spine tier assignment

- **FR-25 (confirm-then-write in PRD) vs AD-3's Binds list — consistent.** AD-3 explicitly binds FR-25 ("Data-Completeness Gate inferred field-value suggestion") alongside FR-16, FR-5, FR-26, FR-27, matching PRD §6's confirm-then-write bucket exactly. No inconsistency.

- **FR-29 (confirm-then-write per PRD §6's literal text) vs AD-12 (direct-write, not AD-3) — a real, unflagged categorization mismatch, though the underlying behavior is defensible.** PRD §6 explicitly lists FR-29 inside the confirm-then-write tier: "confirm-then-write, where Yoh proposes or drafts something and nothing is written until Spencer explicitly confirms it (FR-25, FR-26, FR-27, **FR-29**)." AD-3's own text states the opposite: "Also does not bind: FR-29 (file search result to Research Vault) — see AD-12; FR-29 is modeled as direct-write, the same shape as FR-24, not a Proposal."
  - On substance, the spine's reading is defensible: FR-29's own FR text and testable consequences (§5.8) never describe a "show a draft, then confirm" step the way FR-26 explicitly does ("drafts the item, shows the draft, and creates it only on Spencer's explicit confirmation"). FR-29 only requires that filing follow an explicit, separate request ("save that") — structurally identical to FR-24's direct-write shape, where "the answer itself is the confirmation."
  - On process, though, this is a real discrepancy between two "final" documents that the spine does not surface or reconcile anywhere — AD-3's "does not bind" note explains its own reasoning but never notes that this diverges from PRD §6's own explicit FR-29 placement. A careful reconciliation pass should either (a) get PRD §6 corrected in a future update to move FR-29 into direct-write alongside FR-24 (the PRD's own tier definitions actually support this — FR-29 fits the "explicit request is the confirmation" shape, not the "propose/draft" shape), or (b) have the spine explicitly flag the divergence rather than silently re-categorizing. Recommend flagging to Spencer for a PRD §6 wording fix — low cost, closes a document-consistency gap outright.

## Summary of findings by severity

1. **Real, actionable** — AD-4's "OAuth-scope-level guarantee unchanged" claim is inconsistent with AD-10's single-shared-`OAuth2Client` design once AD-13 widens that client's primary-calendar grant to read/write. The automatic path's stated API-layer defense-in-depth is weakened, and the spine doesn't acknowledge this. (§3 above)
2. **Real, minor** — PRD §6 explicitly places FR-29 in the confirm-then-write tier; AD-3 explicitly places it in direct-write instead, and the spine never flags that it's deviating from the PRD's own written categorization, even though the substantive call is defensible. (§4 above)
3. **Minor gap** — Chat-receipt requirement (FR-26, FR-27 consequences; NFR-DataIntegrity text) has no home anywhere in the spine (zero mentions of "receipt"), despite being covered in the PRD addendum. (§1 above)
4. **Minor/soft gap** — "No search on every chat turn" Non-Goal is protected only by LLM intent-classification correctness; the one structural backstop (daily call cap) is Deferred, not ADOPTED, and even once built is designed to warn rather than block. Not a spine defect per se (matches the PRD's own deferred-classification framing) but under-flagged as a residual risk compared to how the spine treats similar gaps elsewhere (e.g., AD-7's named "Total-outage detection gap"). (§2 above)
5. **Soft gap** — FR-28's "surfaced honestly, never a confident answer" on search failure has no `YohError.kind` or structural distinction for a legitimate zero-results response vs a real failure. (§1 above)

Everything else checked — FR-25/26/27/28/29's remaining testable consequences, the Non-Goal on raw API access, and the Non-Goal on non-Yoh deletion — is cleanly and in most cases structurally (type-level) satisfied by the spine as written.
