# Adversarial Review — Phase 2 Architecture Spine

**Target:** `ARCHITECTURE-SPINE.md` (updated 2026-09-25) — Phase 2 amendments to AD-1/3/5/7/9/10/11/12; new AD-15..AD-24.
**Method:** for each pair below, two units one level down the tree are each built strictly to the letter of every AD that binds them, by an independent subagent that sees only its own task text plus this spine — no cross-task communication, no shared implementation folklore. The pairs are chosen so each side's compliance is real, not sloppy, and the incompatibility survives anyway.

## Verdict

**Not build-ready as written.** Nine concrete holes found, several severe (silent data loss, a live self-contradiction between two ADs, a proven concurrency bug from `memory-store.ts`'s own history that nothing stops four new Phase 2 store files from independently reintroducing). None require an adversarial subagent to misread its task — every one is two honest, spine-literal readings producing incompatible systems.

## The pairs

1. **`rituals/mid-day-reflow.ts` (FR-9) vs `rituals/reshuffle.ts` + `app/approve-reshuffle.ts` (FR-30–33, AD-19)** — both are "the pipeline that re-plans the rest of today," but AD-19 never says whether an approved reshuffle writes back to `memory-store.ts`'s `Plan` record (`PLAN_KIND`, the same one `mid-day-reflow.ts`'s `putPlan` owns) the way mid-day-reflow does. Built literally, `approve-reshuffle.ts` only touches Calendar (AD-4 narrow client) and `plan-state-store.ts` (Pins/pointer) — never `memory-store.ts`. Result: the stored `Plan` a subsequent Mid-Day Re-Flow reads via `getPlan(store, today)` (confirmed in the real code) is stale the instant a reshuffle is approved, so a later "task ran long" chat re-flow refits around block times that no longer match Calendar reality. If instead a builder *does* wire `approve-reshuffle.ts` to also call `putPlan` (equally AD-1/AD-10-legal — `app/` may call `adapters/`), two independent `putPlan` callers now race with **no shared staleness key**: AD-19's own re-check is a Calendar-event hash, blind to `Plan.version`; `memory-store.ts`'s optimistic concurrency is a `Plan.version` check, blind to Calendar. A drag-approve can pass its own staleness check and still throw a raw `ConflictError` against a concurrently-running re-flow — an outcome AD-19's text never anticipates ("It is never reported as success" only covers partial *Calendar* failure). **Fix:** AD-19 must state explicitly whether `approve-reshuffle.ts` writes `memory-store.ts`'s `Plan`, and if so, pin one shared staleness key (`Plan.version`, not two independent mechanisms) that both reshuffle-apply and mid-day-reflow check.

2. **`rituals/morning-ritual.ts` (cron, "unchanged" per AD-5 Phase 2) vs `app/approve-reshuffle.ts` + `plan-state-store.ts`'s "open reshuffle proposal pointer" (AD-19)** — `memory-store.ts`'s own documented `RitualRun` semantics (read verbatim in the codebase) say the marker "only advances on `morning`'s `delivered` outcome," meaning a crashed/retried `morning` run can legitimately fire **more than once on the same day** before delivery succeeds. `morning-ritual.ts` lives in `rituals/`, which per AD-1 "never imports `app/` either" and has zero awareness of Phase 2's `plan-state-store.ts` reshuffle pointer. A same-day re-run therefore regenerates and overwrites the day's `Plan` with total obliviousness to an open, not-yet-approved reshuffle proposal sitting on top of the *old* Plan. AD-19's staleness re-check only hashes raw Calendar events — if the primary calendar hasn't changed, a stale proposal built against a Plan that no longer exists (superseded by the re-run) passes the check and applies moved-block writes keyed to `PlanBlock.id`s and `PLAN_BLOCK_ID_EXTENDED_PROPERTY` tags from a Plan version that's gone, at best silently no-op'ing (tag not found) or applying wrong-context edits. There is also no stated day-boundary or ritual-regeneration hook that clears/invalidates the reshuffle pointer at all. **Fix:** add an explicit AD-19 rule binding the reshuffle proposal's snapshot to `Plan.version` (not just a Calendar hash) and requiring `morning-ritual.ts` (or a Phase 2 `app/`-layer hook it's allowed to call) to clear any open reshuffle pointer whenever it writes a new `Plan` for that date.

3. **`app/check-off.ts` (+ its commit sweep, AD-20) vs `rituals/night-ritual.ts` / `completion-log.ts` (AD-23)** — AD-20 never pins *which timestamp* `recordCompletion`'s `completedAt` snapshots: the original check-off click (captured before the ~5s undo window) or the sweep/commit instant (which can already be past local midnight for a check-off near the day boundary). Both readings independently satisfy AD-20's literal text ("commits due records on a timer... First `completion-log.ts` `recordCompletion`..."). Concrete failure: a Task checked off at 23:59:58 commits at 00:00:03 the next local day. Under the "click time" convention it's attributed to the day that already had its close-out prompt/escalation run hours earlier — `night-ritual.ts`'s exclusion of "completed today" Tasks and `completion-log.ts`'s `recordActivityDay` streak/heatmap accounting silently disagree with each other and with reality, purely based on which of two equally-compliant builders shipped. This same ambiguity also poisons `desk-metrics.ts`'s on-time-rate `[ASSUMPTION: completedAt ≤ dueDate]` for every near-midnight completion. **Fix:** AD-20 (or AD-23) must state explicitly that `completedAt` is the original check-off instant, captured by `app/check-off.ts` before the undo window starts, never the sweep's own clock read — and that "today" for close-out exclusion and activity-day attribution is always derived from that same stamped value.

4. **`web/`'s Reshuffle Preview view (drag hook + unmount handling) vs `app/request-reshuffle.ts` / `plan-state-store.ts`'s proposal lifecycle (AD-19)** — AD-19 assigns "navigating away deletes it" as a stated behavior without assigning *whose* responsibility it is. A `web/`-side builder implements it as a best-effort unload beacon on the Reshuffle Preview component (the only place that can detect "navigating away" at all, since AD-17/AD-18 make the server otherwise blind to client navigation). A server-side builder, following the exact reasoning AD-20 uses elsewhere to justify *not* trusting the browser tab to survive, reasonably treats "new drag supersedes the previous one" as the only real enforcement and leaves the proposal open indefinitely otherwise — consistent with AD-19's own text, which states supersession but never a server-side TTL. On a PWA (AD-15, mobile/backgrounding-prone), unload beacons are unreliable; the result is an open reshuffle proposal that lingers with no server-side expiry, directly feeding failure #2 above. **Fix:** AD-19 needs an explicit, server-enforced expiry (e.g., proposal auto-discards at local day end or after N minutes of inactivity) — never rely on client unload signals as the sole clearing mechanism.

5. **`job-store.ts`'s async job runner (AD-21) vs `notification-store.ts`'s outbox (AD-10/AD-18)** — AD-18 requires "every user-visible change, including a new notification, appends one row to an outbox **in the same transaction**." But AD-10 partitions storage strictly by owning file ("no file reads or writes another file's kinds directly; it calls that file's exports"), and every existing store file (`memory-store.ts`, read in full) constructs its **own** `better-sqlite3` `Database` handle and runs its own `.immediate()` transaction. A job's "mark `done`" write (owned by `job-store.ts`) and the resulting `research-ready` notification + outbox row (owned by `notification-store.ts`) are therefore two separate transactions on two separate connection objects — AD-18's "same transaction" guarantee is structurally unreachable across a cross-owner event unless the spine states that all Phase 2 store files must share one process-wide connection (never stated). A crash between the two writes leaves a job silently marked `done` with no outbox row ever appended — exactly the "event the open Web App never learns about" AD-18 says it prevents. **Fix:** either name a single shared `Database` connection all Phase 2 store files must open against (with a documented cross-owner transaction helper), or relax AD-18 to an explicit two-phase/retry-tolerant contract (e.g., a reconciliation sweep that notices a `done` job with no matching notification) instead of a same-transaction promise no two independently-owned files can jointly keep.

6. **`app/sandbox-submit.ts` (AD-12, "direct-write... same as FR-24") vs the async job/notification machinery `job-store.ts` establishes for `/research` (AD-21) — a live spine self-contradiction.** AD-12 explicitly calls FR-38's sandbox-card submission a synchronous "direct-write" (implying the HTTP request blocks on `updateTaskField` completing). But AD-18's closed `NotificationKind` union — the same union whose narrowness is meant to structurally *prevent* invalid notification kinds — explicitly reserves `sandbox-complete` and `sandbox-failed`, which only make sense for an **async, job-queued** completion model exactly like `research-ready`/`research-failed`. A builder following AD-12 to the letter ships a fully synchronous submit endpoint that never raises those two notification kinds (dead, unconstructible values in practice). A builder following AD-18's own union literally concludes FR-38 must be job-queued like AD-21, and builds a second async pathway alongside AD-12's mandated direct-write. Both are individually correct readings of their governing AD; together, either two notification kinds are permanently dead or two competing submission pathways exist for the same user action. **Fix:** resolve this at the spine level, not by convention — either drop `sandbox-complete`/`sandbox-failed` from `NotificationKind` (confirming FR-38 stays synchronous, matching AD-12), or amend AD-12 to route FR-38 through the same durable-job pattern as AD-21 (confirming those kinds are real).

7. **`completion-log.ts`'s `recordActivityDay` (AD-23) vs `core/desk-metrics.ts`'s streak/heatmap (AD-23)** — AD-23 says `recordActivityDay(date)` is "called by the server on the first API request of each local day" but never says whether the write itself is idempotent (upsert-by-date) or a plain append, and never says who owns de-duplication. Every existing "singleton per key" writer in the codebase (`putPlan`, `putTimeBudget`, `putOpenInteractionRequest`) upserts; but `completion-log.ts` also owns a genuinely append-style write in the same file (`recordCompletion`, one row per completion). A builder mirroring the file's *other* write discipline for consistency implements `recordActivityDay` as a plain insert too. Since the systemd-supervised server (`Restart=always`) can legitimately restart mid-day, its in-memory "have I already called this today" flag resets on every restart, and a second restart-triggered call inserts a duplicate row for the same date. If `desk-metrics.ts`'s streak/heatmap derives a day's presence from row count rather than mere date existence, one crash-restart silently inflates a day's activity intensity or hours-with-Yoh total. **Fix:** AD-23 must state `recordActivityDay` is an idempotent upsert keyed by date, not an append, independent of how many times the server calls it in one local day.

8. **`routine-store.ts` + `core/work-break-fit.ts`'s Routine placement (AD-24) — a direct spine self-contradiction between the Structural Seed's inline gloss and AD-24's own rule text.** The Structural Seed literally says `work-break-fit.ts` "places Pins **and Routine Blocks as fixed inputs**" (the same phrase used for genuinely immovable Pins/calendar-anchors). AD-24's own rule says the opposite in substance: "the same `core/` fitting step places Routine Blocks... **It may shift them but never drops one**" — i.e. Routines are a third category, shiftable-but-guaranteed, not fixed. A builder following the Structural Seed's gloss anchors Routines exactly like Pins/calendar-anchors (no shift ever); on a day where a Pin and a declared Routine collide in time, this build has no resolution rule and must arbitrarily drop or silently overlap one. A builder following AD-24's rule text instead shifts the Routine to the nearest free slot on conflict — producing a Plan where the rendered Routine time silently disagrees with what Spencer configured in `routine-store.ts`, with no Pin-vs-Routine precedence rule stated anywhere to justify which one yields. **Fix:** reconcile the Structural Seed comment with AD-24's rule (the Seed's "as fixed inputs" phrasing is the one that's wrong and should be corrected to "as anchors that may be shifted but never dropped"), and add an explicit Pin-vs-Routine precedence rule for the collision case.

9. **`plan-state-store.ts`'s Pins vs `core/derived-priority.ts` + `core/work-break-fit.ts`'s ordinary Task population (AD-19)** — AD-19 feeds Pins into the fitting step "as fixed inputs" (additive, like calendar events) but never says the Pinned Task is *removed* from the ordinary `CompleteTask` population before `orderByDerivedPriority`/`fitWorkBreakBlocks` run. A builder who takes "fixed input" literally (an anchor injected alongside calendar events, nothing more) leaves the pinned Task's full record in the normal list handed to the ordinary flexible-placement pass; without an explicit exclusion step, `work-break-fit.ts` places that Task **twice** — once at its pinned time, once via ordinary rhythm placement — double-consuming the day's Time Budget and rendering the same Task in two blocks. A builder who separately reasons (correctly, from AD-2's "no shared mutable state" plus common sense) that a Task already placed shouldn't be re-placed adds a filter — but nothing in AD-19's text requires or even mentions this filter, so it's not a shared, testable contract between whoever builds `rituals/reshuffle.ts`'s Pin-reading logic and whoever builds `work-break-fit.ts`'s Phase 2 extension. **Fix:** AD-19 must state explicitly that a Pinned Task is excluded from the ordinary CompleteTask population handed to `orderByDerivedPriority`/`fitWorkBreakBlocks` for that day, with the Pin's own block being its sole placement.

## Bonus structural finding (not a pair, but load-bearing)

AD-10's Phase 2 bullet claims cron-vs-server SQLite concurrency "is covered unchanged" by the spine's stated rule (optimistic concurrency, version-checked on write). But the actual mechanism that makes that guarantee hold under real cross-process contention — `BEGIN IMMEDIATE` plus a `busy_timeout` pragma, to stop a deferred transaction's `SQLITE_BUSY`/`SQLITE_BUSY_SNAPSHOT` from bypassing the version check entirely — exists only as a code-level fix inside `memory-store.ts`, discovered by a prior review, and is **never elevated into AD-10's own text**. Since each of the four new Phase 2 store files (`plan-state-store.ts`, `notification-store.ts`, `job-store.ts`, `completion-log.ts`) is dispatched as its own file-owned task per AD-9, and each subagent sees only the spine (not `memory-store.ts`'s internal doc comments), at least one of the four is likely to reproduce a plain deferred transaction — reintroducing, independently and silently, the exact race `memory-store.ts` already had to fix once. **Fix:** promote the `BEGIN IMMEDIATE` + `busy_timeout` requirement into AD-10's rule text itself (or a shared `readModifyWrite`-style helper every new store file is required to call), not left as tribal knowledge in one adapter's comments.
