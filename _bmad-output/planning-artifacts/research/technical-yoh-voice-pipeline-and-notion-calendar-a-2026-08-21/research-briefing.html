Executive Summary

Notion and Google Calendar integration (Phase-1 MVP, needed for Sept 2): both are straightforward with well-documented, verified patterns. Use a Notion internal integration token medium [18], respect the ~3 req/s rate limit verified [19], and use the current "Query a data source" endpoint rather than the deprecated one verified [20][21]. For Google Calendar, grant calendar.events and tag every event Yoh creates with a private extended property, filtering on it before any update/delete verified [28] — and move the OAuth consent screen to "In production" immediately, since "Testing" mode silently kills all refresh tokens after 7 days verified [31].

Wake-word/voice pipeline (Phase-3 hardware, not urgent for Sept 2): the landscape is settled enough to commit to now. openWakeWord is the right engine for Pi-class hardware medium [2] (Snowboy is dead verified [1], microWakeWord targets microcontrollers, not the Pi). whisper.cpp (tiny/base) and Piper (medium tier) both run real-time on a Raspberry Pi 5 specifically — a Pi 4 is measurably worse for both independently verified [8][10]. PipeWire, not BlueALSA, is the current default Bluetooth-audio path on Bookworm independently verified [6].

Biggest caveat: no genuine real-world, multi-month retrospective was found for a Pi-based always-listening voice assistant specifically (false-wake rates, thermal behavior, Bluetooth dropout frequency). unverified This is a real open risk for Phase 3, not a confirmed finding either way.

Raspberry Pi Wake-Word & Voice Pipeline (Phase 3)

Landscape & maturity

Snowboy is dead verified [1] — cloud training shut down Jan 2021, repo points to an unmaintained fork. openWakeWord is the actively-maintained current choice, default in Home Assistant's voice architecture verified [3], with ongoing low-intensity maintenance into 2026 medium [2]. microWakeWord exists specifically for ESP32-S3 microcontrollers — that reasoning doesn't apply to a Raspberry Pi [2][4].

For STT, whisper.cpp tiny/base are the real-time tier on Pi-class CPUs; small is ~0.4–0.6x real-time, batch-only medium [9], independently confirmed verified [8]. For TTS, Piper is real-time-capable with no GPU, tier choice depending on the Pi model (see Implementation reality).

Piper's licensing changed materially: rhasspy/piper (MIT) is archived; development moved to OHF-Voice/piper1-gpl, relicensed GPL-3.0 verified [5] (year inferred as 2025 from context). For Yoh — personal, non-distributed — this has no practical effect: GPL obligations attach to distribution, not private use.

Integration & interoperability

Standard chain: wake-word detector → STT → intent/LLM → TTS → audio out. One builder chose a cloud LLM over local inference specifically because local LLM inference (not STT/TTS) was the Pi-class bottleneck low [7b] — a signal, not a fact.

Raspberry Pi OS Bookworm replaced PulseAudio/JACK with PipeWire, which now natively manages Bluetooth reconnection and A2DP output independently verified [6] — most BlueALSA-based Bluetooth-on-Pi tutorials online predate this and describe a superseded default. BlueALSA remains available and preferred by some for headless setups, but isn't the modern default. One open PipeWire-Bluetooth GitHub issue suggests the path isn't universally friction-free yet low-medium [7].

Implementation reality

On a Raspberry Pi 5, whisper.cpp tiny/base and Piper's "medium" tier both run comfortably real-time. On a Raspberry Pi 4, Piper lags 1–3s/sentence at "medium" vs. under 1s on Pi 5 independently verified [10]. STT is tighter still: even on Pi 5, base/small "saturate the CPU" — base.en only becomes viable at all on Pi 5, not Pi 4 independently verified [8]. Build on a Pi 5, not a 3/4 — Pi 4 may not clear the real-time bar at all for STT.

What this research could not find, despite a dedicated follow-up round: a genuine, Pi-specific long-term retrospective on false-wake rates, thermal throttling, or Bluetooth dropout frequency unverified [11]. An ESP32-based device showed no thermal issues over 15 months medium [12] — suggestive, not transferable (different hardware class).

Notion API Integration (Phase 1 MVP)

Landscape & maturity

Current API version, confirmed directly: 2026-03-11 verified [13][14]. A third-party blog's "2026-04-01" claim is incorrect — it conflates the March 19 "Views API" feature addition with a fictitious version bump low [15]. Last genuine breaking change: the 2025-09-03 "data sources" migration — old integrations still work for single-data-source databases like Yoh's verified [16].

Integration & interoperability

Use a Notion internal integration (static token, one workspace, no OAuth) medium [18]. Read via the current "Query a data source" endpoint, not the deprecated databases/{id}/query verified [20][21]. Write via PATCH /pages/{id} — rollup properties are explicitly documented as not updatable; formula properties are implied read-only, not explicitly stated so verified (rollup) [22]. Native webhooks now exist as a polling alternative verified [17] — not needed for Yoh's once-daily model.

Implementation reality

Rate limit: ~3 req/s per integration, same regardless of integration type verified [19] — trivial at personal scale. Date filters without explicit timezone default to UTC low-medium, snippet-level — set timezone explicitly on every date write/filter. Official SDK is JS-only (notion-sdk-js); Python relies on the community notion-client [23][24].

Google Calendar API Integration (Phase 1 MVP)

Landscape & maturity

Still v3, no major-version break; a 2026 update added an eventType field verified [25]. Google actively revising calendar-adjacent policy through 2026 (secondary-calendar cleanup, ownership-transfer API) — doesn't affect Yoh's usage, but signals active churn worth a periodic recheck verified [26].

Integration & interoperability

Auth: a service account cannot access a personal (@gmail.com) calendar — no domain-wide delegation for consumer accounts medium [30]. Use OAuth 2.0 user consent, and critically: move the consent screen to "In production" — "Testing" mode auto-expires all refresh tokens after exactly 7 days verified, official docs [31]. This is directly load-bearing for the Sept 2 MVP.

Write isolation: no scope restricts an app to "only events it created" on the user's existing/primary calendar — that guarantee (calendar.app.created) only applies to a separate app-owned calendar. The verified pattern instead: grant calendar.events, tag every Yoh-created event with a private extended property, always filter on it before update/delete verified [28][29]. No comparison found vs. the dedicated-secondary-calendar alternative in practice.

ICS/iCal subscription still works, but refresh latency is ~8–24h (up to 48h reported) with no published SLA medium [32] — confirms the live-API-for-reads design choice.

Implementation reality

Quotas generous for personal use (10,000 req/min/project) verified [27]. Two anecdotal gotchas: a silent no-op bug updating recurring-event RRULEs medium [33], and some spec-valid RRULEs rejected low-medium [34] — lower priority since Yoh's MVP doesn't use recurrence yet. Recurring events require a single shared timezone medium, snippet-level [35]. Developers commonly report needing to manually persist refreshed tokens back to storage, and some run a keep-alive cron against ~6-month staleness medium, multi-source [36][37].

Cross-Dimension Insights

  • The Sept-2 MVP and the Phase-3 hardware build share almost no technical risk — Notion/Calendar integration is low-risk and well-documented; the wake-word pipeline's one real unknown (long-term Pi reliability) sits entirely in Phase 3, which the roadmap already deferred past the MVP. This research validates that sequencing, rather than complicating it.
  • Both integrations independently converged on the same pattern: tag what you own, touch only what you tagged — Notion's rollup/formula read-only boundary and Calendar's extended-properties self-tagging are both instances of "never assume write access beyond what you explicitly created." Consistent with the "propose, don't impose" trust boundary already in Yoh's design.
  • The OAuth "Testing status" 7-day token expiry is the single highest-risk item for the Sept 2 MVP — not hard to fix, but exactly the kind of thing that looks fine at first and fails silently a week later.

Recommendations

1. Notion (Phase 1, Sept 2) — internal integration token; query via the current data-source endpoint, not the deprecated one. High confidence on versioning/endpoint shape [13][20][21]; the token-pattern recommendation itself is medium confidence [18] — worth a 2-minute direct doc check.
Feeds: architecture spine (integration approach) · roadmap risk (low)
2. Google Calendar (Phase 1, Sept 2) — grant calendar.events, tag Yoh-created events, and move the OAuth consent screen to "In production" before relying on it daily. High confidence, primary-source-verified.
Feeds: architecture spine (auth pattern) · roadmap risk (currently the MVP's single highest silent-failure risk if skipped)
3. Hardware (Phase 3) — build on a Raspberry Pi 5, target openWakeWord + whisper.cpp (tiny/base) + Piper (medium) over PipeWire's Bluetooth path. High confidence on Snowboy's death, Pi 5 performance, PipeWire default; medium confidence on openWakeWord-over-microWakeWord specifically.
Feeds: architecture spine (hardware baseline) · roadmap estimate
4. Before committing further to Phase 3 — run a short real-world spike testing wake-word false-positive/negative rate and Bluetooth reliability in the actual bathroom/bedroom setup. This is the one dimension published evidence couldn't answer.
Feeds: roadmap risk (Phase 3 estimate should carry a buffer)

  • unverified Whether "primary calendar + extendedProperties" or "dedicated secondary calendar" is more common in practice — both are mechanically valid; no practitioner consensus found.
  • low, snippet-level Notion's UTC-default timezone-filter behavior and formula-property read-only status rest on snippet-level confirmation, not a direct docs fetch.
  • disputed Google Calendar recurring-event gotchas (silent no-op, RRULE rejection) are single-source/anecdotal — not currently relevant since Yoh's MVP doesn't create recurring events; re-check before adding recurrence later.
