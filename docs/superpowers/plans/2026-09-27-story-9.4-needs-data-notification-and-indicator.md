# Story 9.4 — Needs-Data Notification and Indicator Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the loop Story 9.1's two-tier gate opened and Story 9.2's `/sandbox` queue computes: when the Morning Ritual (6am cron, or an on-demand `/plan`) finds one or more Tasks it couldn't place because a Required field is missing, it raises one `needs-data` in-app notification — "{n} Tasks need data to be placed" — deep-linking to Chat with `/sandbox` already running. The same live count also renders persistently on the Tasks page header as the Needs-Data Indicator ("3 need data", hidden at 0), reading the identical `app/sandbox-queue.ts` computation through a new `GET /api/sandbox/count` route, and refetching whenever a `tasks`/`sandbox` outbox hint says the count might have moved. Neither surface keeps its own count (AD-11) — both are thin, freshly-fetched views over one server-side computation. An unplaced Task is therefore always reachable two ways (indicator or notification) and never rendered with a guessed Due Date or Estimated Duration anywhere on the web surface (FR-34).

**Architecture:** Two independent read paths off the same underlying rule (`core/data-completeness-gate.ts`'s `checkDataCompleteness`, reshaped by Story 9.1 to gate on Required fields only), never a shared mutable count. (1) `rituals/morning-ritual.ts`'s `runMorningRitual` already computes `incompleteTaskIds` at its own Data-Completeness Gate step (step 3) on every run; this story adds one notification raise right after that computation, gated only on `incompleteTaskIds.length > 0`, applying uniformly to every run outcome (`nothing-to-plan`, `nothing-fits`, `delivered` alike — an incomplete Task is exactly as real on a day nothing else could be planned). The raise goes through `createNotificationInTx` inside the caller's shared `writeTx`, wrapped non-fatally (a notification-write failure must never block reporting today's Plan outcome), exactly mirroring `app/check-off.ts`'s own `operational`-notification pattern. This requires threading the process's `SqliteConnection` into `MorningRitualDeps` as a new optional field, wired from both callers that build one — `shell/ritual-cli/morning-deps.ts` (the 6am cron) and `app/plan-day.ts` (the on-demand `/plan` path) — so the notification fires identically from either. (2) `web/src/components/NeedsDataIndicator.tsx` is a small polling component (mirrors `web/src/lib/tasks.ts`'s `useTasksList` shape, not the heavier `useSyncExternalStore` session-store family Story 9.2's `sandbox.ts` needs) that fetches `GET /api/sandbox/count` on mount and on any `tasks`/`sandbox` outbox hint from the one shared event bus, mounted in `web/src/pages/Tasks.tsx`'s header. The route itself is a thin transport wrapper: `shell/server.ts` calls Story 9.2's `sandboxQueue({})` and maps `.items.length` into `{count}` — no new `app/*.ts` file, matching the existing `/api/commands` route's own "call straight through, no extra layer" precedent.

**A hard layering constraint this design works around (flagged prominently — see Assumptions #1 below):** Story 9.4's SDD implementer notes say to build the notification's count/body "from `sandboxQueue`'s own item list... don't recompute a parallel count from `incompleteTaskIds` by hand." Taken completely literally that would mean `rituals/morning-ritual.ts` importing `app/sandbox-queue.ts` — but AD-1 (enforced by `tests/layering-rules.test.ts`'s Rule 1) forbids `rituals/*.ts` **and** every file under `shell/ritual-cli/*` from importing anything under `app/`, with no exception carved out here. There is no seam through which the 6am cron path could reach the real `sandboxQueue` even if this plan wanted it to. This plan resolves the tension by reading the count off `gate.value.incomplete` — the exact same `checkDataCompleteness` call Story 9.1's gate makes, which is **also** the one function `sandboxQueue` itself calls to answer the identical question. The two can never disagree on the *rule* (both call the one gate); they simply each take their own fresh Notion read, which is inherent to a "computed, not stored" design (`sandboxQueue` itself re-reads fresh on every call, so its own count already varies moment-to-moment independent of this ritual's read). This is flagged for the controller to confirm; see Assumptions #1.

**Tech Stack:** `node:test` for `src/` (real throwaway `:memory:` SQLite via `openSqliteConnection`, same convention as `tests/check-off-app.test.ts`); Vitest + RTL for the new web component; Playwright for the e2e smoke addition. No new packages.

**Spec:** `_bmad-output/planning-artifacts/architecture/architecture-YohV1-2026-08-22/ARCHITECTURE-SPINE.md` AD-1, AD-5, AD-10, AD-11, AD-17, AD-18; `_bmad-output/planning-artifacts/epics.md`, "Story 9.4: Needs-Data Notification and Indicator"; `_bmad-output/planning-artifacts/ux-designs/ux-YohV1-2026-08-21/DESIGN.md`, UX-DR42 ("Needs-Data Indicator") and the `typography.numerals`/Secondary-button rim rows; `_bmad-output/implementation-artifacts/sdd-plan-YohV1-phase2-epic9.md` Task 4 (Epic 9 Interface Contract E5/E7/E8/E9/E10, and Task 4's own Owns/Implementer-notes/Controller-rulings/ACs).

- **AD-10 (storage):** `adapters/sqlite.ts` stays the only opener; the notification write goes through the caller's shared `writeTx` (`createNotificationInTx`), never a second connection.

- **Tone (FR-18, FR-19, FR-42; polish-1):** the notification body is the one plain sentence the AC gives verbatim — "{n} Tasks need data to be placed" — no filler, no internal names, no ISO timestamps; title and body are identical (the established convention for a short, single-line notification card, per `web/src/components/NotificationOverlay.tsx`'s own "several notification kinds... pass title === body" doc comment).

Tests start green and stay green after this task — every new/changed dependency (`MorningRitualDeps.connection`, `ServerDeps.sandbox`) is optional, so no existing call site or test breaks by omission.

## Review Focus

Five failure modes the ACs imply but no other step in this plan already pins on its own — each gets its own test in the step named.

1. **No notification when the count is zero**, even though every other precondition (an incomplete-capable run, a wired `connection`) is met — the AC's explicit negative case ("No notification is raised when the count is zero"), easy to get backwards if the guard is written as "connection present" instead of "count > 0 AND connection present." Pinned in Task 1, Step 3.
2. **The notification fires on a `nothing-to-plan` (or `nothing-fits`) run, not only a `delivered` one** — the single most common real case (every Task missing a Required field) is also the one a naive implementation nested inside the `"delivered"` branch would silently skip. Pinned in Task 1, Step 4.
3. **The on-demand `/plan` path raises the identical notification** — the implementer note's explicit requirement ("must fire from an on-demand `/plan` run exactly as it does from the 6am cron run") is easy to satisfy for the cron wiring alone and forget for `plan-day.ts`, since the two deps builders are edited in different files with no shared test. Pinned in Task 3, Step 2.
4. **The Needs-Data Indicator never shows a stale, guessed, or zero count** — hidden while loading, hidden at exactly 0, and (the easy miss) hidden rather than showing a leftover/wrong number when the fetch itself fails. Pinned in Task 5, Step 2.
5. **Clicking the Indicator runs `/sandbox` immediately, not just opens an empty Chat panel** — the AC says "clicking it opens Chat with `/sandbox` started," which a partial implementation could satisfy by only calling `openChatPanel()` and stopping there. Pinned in Task 5, Step 2.

 * web/src/components/NeedsDataIndicator.tsx

 * source for this count is `app/sandbox-queue.ts`'s `sandboxQueue`, reached
 * here through `GET /api/sandbox/count` — this component keeps no count of
 * its own beyond whatever the server just returned.

 * Refetches on mount, and on any `tasks` or `sandbox` outbox hint over the
 * one shared event bus (`eventBus.ts`, AD-18) — a Task's Due Date or
 * Estimated Duration changing (the Tasks page, `/sandbox`) is exactly what
 * can move this count. Clicking it opens the Chat panel AND immediately
 * runs `/sandbox` (`openChatWithCommand`, Story 9.3's E8 deep-link
 * convention) — never the panel alone.

import { useCallback, useEffect, useRef, useState } from "react";
import { apiClient } from "../lib/apiClient.ts";
import { onHint } from "../lib/eventBus.ts";
import { openChatWithCommand } from "../lib/chatPanel.ts";

/** Hint topics that can change how many Tasks need data. */
const REFETCH_TOPICS = new Set(["tasks", "sandbox"]);

export function NeedsDataIndicator(): React.JSX.Element | null {
  const [count, setCount] = useState<number | undefined>(undefined);
  const latest = useRef(0);

  const refetch = useCallback(async (): Promise<void> => {
    const seq = ++latest.current;
    try {
      const res = await apiClient.api.sandbox.count.$get();
      const body = (await res.json()) as { ok: true; value: { count: number } } | { ok: false; error: { message: string } };
      if (seq !== latest.current) return;
      setCount(body.ok ? body.value.count : undefined);
    } catch {
      if (seq !== latest.current) return;
      setCount(undefined);
    }
  }, []);

  useEffect(() => {
    void refetch();
  }, [refetch]);

  useEffect(
    () =>
      onHint((hint) => {
        if (REFETCH_TOPICS.has(hint.topic)) void refetch();
      }),
    [refetch],
  );

  if (!count) return null; // hides at 0 AND while the count is still unknown/failed

  return (
    <button
      type="button"
      onClick={() => openChatWithCommand("/sandbox")}
      className="flex h-[38px] shrink-0 items-center gap-1.5 rounded-full border-[length:var(--rim-width)] border-rim-interactive bg-transparent px-3 font-body text-ink-primary focus-visible:outline-[length:var(--focus-ring-width)] focus-visible:outline-offset-2 focus-visible:outline-accent-solid"
    >
      <span role="status" aria-live="polite" className="text-numerals font-bold tabular-nums">
        {count}
      </span>
      <span className="text-small text-ink-secondary">need data</span>
    </button>
  );
}
