# Story 7.10: Check Off a Task With Undo — Implementation Plan

> **As built (implementer, 2026-09-26): deviations from the task code below.** The ACs, the spine (AD-20, AD-23), the controller rulings (R7, R8, R16), and the real code as built win where this plan's code disagreed. No new packages.
> - **The Status write is called from `app/check-off.ts`, never bound in `shell/server.ts`.** `tests/layering-rules.test.ts` (AD-16) fails any non-allowlisted `shell/*.ts` that even names the write function, so this plan's `buildCheckOffDeps` binding (and its `CheckOffDeps.setTaskStatus` function dep) couldn't exist. `CheckOffDeps` instead takes `notionClient` + `notionStatusConfig`, and `app/check-off.ts` calls `notion-adapter.ts`'s real Status-only write itself. Tests drive it through a fake client (`tests/fakes/fake-notion-status-client.ts`: `dataSources.retrieve` returns a live Status schema, `pages.update` records or throws), so the real `closestOption` resolution runs too.
> - **Ruling R7's Task lookup runs at commit, not on the click.** A live lookup is a full `readNotionTasks` read; doing it inside `checkOff` would delay the response (and so the toast) by Notion's latency and eat into the window. `checkOff` touches only local SQLite and names the record from today's stored Plan row; `commitDueCheckOffs` looks the Task up just before `recordCompletionInTx` (the completion is written then; the window is ~5 s, so the values are the click-time ones). A lookup failure still never blocks: nulls for the three fields, the Plan label as `taskName`, and a logged `check-off.lookup-failed`. The client still sends only `{taskId}`; `HomePlanRow`/`HomeViewResponse` are unchanged.
> - **Pending-record lifecycle made crash- and race-safe.** Columns: `task_id, task_name, completed_at, commit_at, held_since, committed_at, notion_sync_pending, notion_failure_notified, notion_retry_at` (area/dueDate/estimatedMinutes aren't stored — they're snapshotted at commit). The commit **claims** the record (`claimDueCheckOffInTx`, which re-checks due-ness) in the SAME `writeTx` as `recordCompletionInTx` and the outbox hint, so an Undo racing the sweep either wins or gets `conflict`, and a retry can never re-run `recordCompletion`. The Notion write happens after that transaction, outside it. Overlapping sweeps can't double-write Notion either (`leaseNotionRetryInTx`; the claim takes the first lease). The first Notion failure alone raises the notification (`markNotionSyncFailedInTx` returns `true` once).
> - **Notion retries back off: `CHECK_OFF_NOTION_RETRY_MS = 60_000`** (one export, `app/check-off.ts`). "Retried on the next sweep" read literally means once per 1 s commit tick, which would hammer Notion's ~3 req/s limit (each retry is a schema read plus a write) for the whole outage. The sweep still runs every tick; a failed record is simply due for retry a minute later.
> - **A hold can't strand a check-off: `CHECK_OFF_MAX_HOLD_MS = 600_000`** (one export, `plan-state-store.ts`). A tab closed or asleep mid-hover would otherwise hold the record forever, contradicting AD-20's "regardless of whether the browser tab still exists". Past 10 minutes the hold is ignored and the record commits.
> - **`UNDO_WINDOW_MS` stays in `plan-state-store.ts`** (per the brief). The client never sees it: every check-off/hold/release response is `PendingCheckOffResponse {id, taskId, commitAt, asOf, held}` (new shape in `types/api.ts`), and the toast runs for `commitAt - asOf` — two server timestamps — so a skewed browser clock can't shorten or stretch the window.
> - **Undo of anything no longer pending is `conflict`** (not `validation`): once a record has synced to Notion it's deleted, so "already committed" and "unknown id" can't be told apart, and both mean "too late" to the client.
> - **A repeated check of the same Task returns its existing pending record** rather than creating a second one (a reload mid-window shows the row unchecked again, since the server doesn't count uncommitted records; a second click must never produce two completions).
> - **Outbox topic: `"plan"`, on commit only.** Home's store (7.8) already re-fetches on `"plan"`, and a commit is exactly what changes Home's server view (the row turns `completed`), so no new topic or listener is needed. **Goal:** Checking a Plan Row's Checkbox dissolves it instantly, client-side, before any server response. The server records a pending completion with a ~5s undo window, commits it (Completion Log, then Notion Status) on a timer or a startup sweep if the tab is long gone, and retries a failed Notion write on the next sweep — never rolling back the log.

**Architecture:** `plan-state-store.ts` (Story 7.4's heartbeat-only file) gains its second table, `pending_check_offs`, and the one defining export `UNDO_WINDOW_MS`. A row's lifecycle is three states, tracked by two nullable columns rather than a status enum: `held_since IS NOT NULL` (the toast is hovered/focused — `commit_at` shifts forward by exactly the held duration on release, so "the timer effectively pauses" without a separate pause/resume clock); `committed_at IS NULL` (still pending, eligible for the due-sweep); `committed_at IS NOT NULL AND notion_sync_pending = 1` (the log entry is written, Notion failed, eligible for the retry-sweep only — never re-runs `recordCompletion`). `app/check-off.ts` owns the whole state machine: `checkOff` looks up the Task's CURRENT `area`/`dueDate`/`estimatedMinutes` from Notion itself (an injected `lookupTask`, mirroring Story 7.9's Ruling R7 exactly — the client sends only `{taskId}`, never these three fields, so `HomeViewResponse`/`HomePlanRow` (Story 7.8, already locked) need no widening) before creating the pending record; a lookup failure never blocks recording it (`R7`). `commitDueCheckOffs` is the one sweep function, called by both `shell/server.ts`'s commit timer and its own startup sweep — commit order is fixed: `completion-log.ts`'s `recordCompletion` (its own transaction, done and durable before anything else happens) first, then `setTaskStatus(completed)` as a separate step (an external API call is never held inside the same DB transaction as the log write). On the client, `web/src/components/PlanChecklist.tsx` owns per-row optimistic state (a `Set` of locally-checked task ids, cleared only by a server refetch) and exactly one visible Undo Toast at a time — UX OQ7's resolution: several rapid check-offs each get an independent pending record and commit independently server-side, but only the newest has a visible toast; an earlier one's row stays dissolved and commits silently, un-undoable from the UI once superseded.

**Tech Stack:** existing `better-sqlite3`/`node:test` server-side conventions; `useSyncExternalStore`/CSS transitions client-side; Playwright for the two-flow smoke, run against the server with a fake Notion client (an env-gated in-memory fixture — no real Notion account touched in tests).

**Spec:** SDD plan Task 10 (`_bmad-output/implementation-artifacts/sdd-plan-YohV1-phase2.md`); `ARCHITECTURE-SPINE.md` AD-20 (check-off commit mechanics), AD-23 (`recordCompletion`'s pinned signature) with Ruling R7 (`docs/superpowers/plans/2026-09-25-story-7.9-completion-log-status-only-writes.md`, "Open questions"/Ruling R7 section); `DESIGN.md` `checkbox`/`undo-toast`; `EXPERIENCE.md` Component Patterns (Undo Toast), Open Question 7 (resolved above).

## Global Constraints

- The Checkbox's visual check (checkmark + strikethrough + 50% opacity, then dissolve) happens client-side, instantly, before any server response (NFR-Latency) — instant hide, no fade, under reduced motion.
- `UNDO_WINDOW_MS` is exported exactly once, from `plan-state-store.ts` — the client never hard-codes it; every response that starts a countdown returns the real `commitAt`.
- Commit order is fixed: `recordCompletion` (`source: 'check-off'`) first, then `setTaskStatus(completed)` — never the reverse, never skipped on either side independently.
- A Notion failure at commit keeps the Completion Log entry, marks the row pending for retry, and raises exactly one `operational` notification worded `"Couldn't update Notion for {Task} — retrying"` — it never rolls back the log, and a later failed retry does not raise a second notification for the same row.
- `check-off.ts` supplies `area`/`dueDate`/`estimatedMinutes` to `recordCompletion` from a live Notion lookup (Ruling R7) — never from client input, never widening `types/api.ts`'s existing `HomePlanRow`/`HomeViewResponse`.
- While an Undo Toast is hovered or focused, the pending record's timer is held — released, it resumes with exactly the remaining time it had (WCAG 2.2.1).
- Several rapid check-offs each commit independently; only the newest has a visible Undo Toast.
- The Playwright smoke never performs a real Notion write.

```ts
import { randomUUID } from "node:crypto";

/** ~5s (AD-20, `[ASSUMPTION]`) — the ONE defining export for this shared tuning constant. The response to every check-off returns the real `commitAt`; the client never hard-codes this. */
export const UNDO_WINDOW_MS = 5000;

// Extend initPlanStateStoreSchema (keep the existing heartbeat CREATE TABLE, add):
export function initPlanStateStoreSchema(db: Database.Database): void {
  db.exec(`CREATE TABLE IF NOT EXISTS heartbeat (id INTEGER PRIMARY KEY CHECK (id = ${HEARTBEAT_ROW_ID}), at TEXT NOT NULL)`);
  db.exec(`
    CREATE TABLE IF NOT EXISTS pending_check_offs (
      id TEXT PRIMARY KEY,
      task_id TEXT NOT NULL,
      task_name TEXT NOT NULL,
      area TEXT,
      due_date TEXT,
      estimated_minutes INTEGER,
      completed_at TEXT NOT NULL,
      commit_at TEXT NOT NULL,
      held_since TEXT,
      committed_at TEXT,
      notion_sync_pending INTEGER NOT NULL DEFAULT 0
    );
  `);
}

export interface PendingCheckOff {
  readonly id: string;
  readonly taskId: string;
  readonly taskName: string;
  readonly area: string | null;
  readonly dueDate: string | null;
  readonly estimatedMinutes: number | null;
  readonly completedAt: string;
  readonly commitAt: string;
  readonly heldSince?: string;
  readonly committedAt?: string;
}

export interface CreatePendingCheckOffInput {
  readonly taskId: string;
  readonly taskName: string;
  readonly area: string | null;
  readonly dueDate: string | null;
  readonly estimatedMinutes: number | null;
  readonly completedAt: string;
}

interface PendingCheckOffRow {
  readonly id: string;
  readonly task_id: string;
  readonly task_name: string;
  readonly area: string | null;
  readonly due_date: string | null;
  readonly estimated_minutes: number | null;
  readonly completed_at: string;
  readonly commit_at: string;
  readonly held_since: string | null;
  readonly committed_at: string | null;
}

function rowToPendingCheckOff(row: PendingCheckOffRow): PendingCheckOff {
  return {
    id: row.id,
    taskId: row.task_id,
    taskName: row.task_name,
    area: row.area,
    dueDate: row.due_date,
    estimatedMinutes: row.estimated_minutes,
    completedAt: row.completed_at,
    commitAt: row.commit_at,
    ...(row.held_since !== null ? { heldSince: row.held_since } : {}),
    ...(row.committed_at !== null ? { committedAt: row.committed_at } : {}),
  };
}

export function createPendingCheckOffInTx(db: Database.Database, input: CreatePendingCheckOffInput): string {
  const id = randomUUID();
  const commitAt = new Date(Date.parse(input.completedAt) + UNDO_WINDOW_MS).toISOString();
  db.prepare(
    `INSERT INTO pending_check_offs (id, task_id, task_name, area, due_date, estimated_minutes, completed_at, commit_at)
     VALUES (@id, @taskId, @taskName, @area, @dueDate, @estimatedMinutes, @completedAt, @commitAt)`,
  ).run({ id, taskId: input.taskId, taskName: input.taskName, area: input.area, dueDate: input.dueDate, estimatedMinutes: input.estimatedMinutes, completedAt: input.completedAt, commitAt });
  return id;
}

export function createPendingCheckOff(connection: SqliteConnection, input: CreatePendingCheckOffInput): string {
  return connection.writeTx((db) => createPendingCheckOffInTx(db, input));
}

export function getPendingCheckOff(connection: SqliteConnection, id: string): PendingCheckOff | undefined {
  const row = connection.db.prepare<{ id: string }, PendingCheckOffRow>(`SELECT * FROM pending_check_offs WHERE id = @id`).get({ id });
  return row ? rowToPendingCheckOff(row) : undefined;
}

export function listDuePendingCheckOffs(connection: SqliteConnection, now: Date): PendingCheckOff[] {
  const rows = connection.db
    .prepare<{ now: string }, PendingCheckOffRow>(`SELECT * FROM pending_check_offs WHERE committed_at IS NULL AND held_since IS NULL AND commit_at <= @now ORDER BY commit_at`)
    .all({ now: now.toISOString() });
  return rows.map(rowToPendingCheckOff);
}

export function listNotionRetryCheckOffs(connection: SqliteConnection): PendingCheckOff[] {
  const rows = connection.db
    .prepare<[], PendingCheckOffRow>(`SELECT * FROM pending_check_offs WHERE committed_at IS NOT NULL AND notion_sync_pending = 1`)
    .all();
  return rows.map(rowToPendingCheckOff);
}

/** WCAG 2.2.1: while hovered/focused, the pending record is held — it never appears in `listDuePendingCheckOffs`. */
export function holdPendingCheckOff(connection: SqliteConnection, id: string, at: string): void {
  connection.db.prepare(`UPDATE pending_check_offs SET held_since = @at WHERE id = @id AND held_since IS NULL`).run({ id, at });
}

/** Shifts `commit_at` forward by exactly the held duration, so the timer "resumes" with the same remaining time it had (never less, never more). */
export function releasePendingCheckOff(connection: SqliteConnection, id: string, at: string): void {
  const row = connection.db.prepare<{ id: string }, { held_since: string | null; commit_at: string }>(`SELECT held_since, commit_at FROM pending_check_offs WHERE id = @id`).get({ id });
  if (!row || row.held_since === null) return;
  const heldMs = Date.parse(at) - Date.parse(row.held_since);
  const newCommitAt = new Date(Date.parse(row.commit_at) + heldMs).toISOString();
  connection.db.prepare(`UPDATE pending_check_offs SET held_since = NULL, commit_at = @commitAt WHERE id = @id`).run({ id, commitAt: newCommitAt });
}

export function removePendingCheckOff(connection: SqliteConnection, id: string): void {
  connection.db.prepare(`DELETE FROM pending_check_offs WHERE id = @id`).run({ id });
}

export function markCommittedNotionPending(connection: SqliteConnection, id: string, committedAt: string): void {
  connection.db.prepare(`UPDATE pending_check_offs SET committed_at = @committedAt, notion_sync_pending = 1 WHERE id = @id`).run({ id, committedAt });
}
```

```ts
/**
 * src/app/check-off.ts
 *
 * Story 7.10, AD-16/AD-20. The Web client sends only `{taskId}` — this file
 * looks up the Task's CURRENT area/dueDate/estimatedMinutes itself, live,
 * before creating the pending record (Story 7.9's Ruling R7), so
 * `types/api.ts`'s already-locked `HomePlanRow`/`HomeViewResponse` (Story
 * 7.8) need no widening. A lookup failure never blocks recording the
 * pending check-off — it just records `null` for the three fields, exactly
 * the close-out path's own precedent.
 */
import {
  createPendingCheckOff,
  getPendingCheckOff,
  holdPendingCheckOff,
  listDuePendingCheckOffs,
  listNotionRetryCheckOffs,
  markCommittedNotionPending,
  releasePendingCheckOff,
  removePendingCheckOff,
  type PendingCheckOff,
} from "../adapters/plan-state-store.ts";
import { recordCompletionInTx } from "../adapters/completion-log.ts";
import { appendOutboxInTx, createNotificationInTx } from "../adapters/notification-store.ts";
import type { SqliteConnection } from "../adapters/sqlite.ts";
import type { ExternalId, Result, Task, TaskStatus, YohError } from "../types/domain.ts";

export const CHECK_OFF_COMMIT_TICK_MS = 1000;

export interface CheckOffDeps {
  readonly connection: SqliteConnection;
  /** A live per-id Notion Task lookup (Ruling R7) — chat-cli.ts/server.ts wire this to `readNotionTasks(...).tasks.find(t => t.id === taskId)`, same as Story 7.9's close-out path. */
  readonly lookupTask: (taskId: ExternalId) => Promise<Task | undefined>;
  /** `notion-adapter.ts`'s Status-only `setTaskStatus`, pre-bound. */
  readonly setTaskStatus: (taskId: ExternalId, status: TaskStatus) => Promise<Result<void, YohError>>;
  readonly now: () => Date;
  readonly log?: (entry: Record<string, unknown>) => void;
}

function describeError(err: unknown): string {
  return err instanceof Error ? err.message : String(err);
}

export interface CheckOffInput {
  readonly taskId: ExternalId;
}

export async function checkOff(deps: CheckOffDeps, input: CheckOffInput): Promise<Result<{ id: string; commitAt: string }, YohError>> {
  let task: Task | undefined;
  try {
    task = await deps.lookupTask(input.taskId);
  } catch (err) {
    deps.log?.({ level: "error", event: "check-off.lookup-failed", taskId: input.taskId, message: describeError(err) });
    task = undefined; // R7: a lookup failure never blocks recording the completion.
  }

  const completedAt = deps.now().toISOString();
  const id = createPendingCheckOff(deps.connection, {
    taskId: input.taskId,
    taskName: task?.title ?? input.taskId,
    area: task?.area ?? null,
    dueDate: task?.dueDate ?? null,
    estimatedMinutes: task?.estimatedDurationMinutes ?? null,
    completedAt,
  });
  const pending = getPendingCheckOff(deps.connection, id)!;
  return { ok: true, value: { id, commitAt: pending.commitAt } };
}

export interface CheckOffIdInput {
  readonly id: string;
}

export async function undoCheckOff(deps: CheckOffDeps, input: CheckOffIdInput): Promise<Result<Record<string, never>, YohError>> {
  const row = getPendingCheckOff(deps.connection, input.id);
  if (!row) return { ok: false, error: { kind: "validation", message: `check-off: no pending check-off ${input.id}` } };
  if (row.committedAt !== undefined) return { ok: false, error: { kind: "conflict", message: "check-off: already committed — can't undo" } };
  removePendingCheckOff(deps.connection, input.id);
  return { ok: true, value: {} };
}

export async function holdCheckOff(deps: CheckOffDeps, input: CheckOffIdInput): Promise<Result<Record<string, never>, YohError>> {
  holdPendingCheckOff(deps.connection, input.id, deps.now().toISOString());
  return { ok: true, value: {} };
}

export async function releaseCheckOff(deps: CheckOffDeps, input: CheckOffIdInput): Promise<Result<{ commitAt: string }, YohError>> {
  releasePendingCheckOff(deps.connection, input.id, deps.now().toISOString());
  const row = getPendingCheckOff(deps.connection, input.id);
  if (!row) return { ok: false, error: { kind: "validation", message: `check-off: no pending check-off ${input.id}` } };
  return { ok: true, value: { commitAt: row.commitAt } };
}

async function commitOne(deps: CheckOffDeps, row: PendingCheckOff): Promise<void> {
  const alreadyCommitted = row.committedAt !== undefined;
  if (!alreadyCommitted) {
    deps.connection.writeTx((db) => {
      recordCompletionInTx(db, {
        taskId: row.taskId,
        taskName: row.taskName,
        area: row.area,
        dueDate: row.dueDate,
        estimatedMinutes: row.estimatedMinutes,
        completedAt: row.completedAt,
        source: "check-off",
      });
      appendOutboxInTx(db, { topic: "plan", entityId: row.taskId });
    });
  }

  const statusResult = await deps.setTaskStatus(row.taskId, "completed");
  if (statusResult.ok) {
    removePendingCheckOff(deps.connection, row.id);
    return;
  }

  if (!alreadyCommitted) {
    // First failure only — mark for retry AND raise the one notification.
    // A later retry that also fails must not raise a second one (checked
    // via `alreadyCommitted` on the NEXT commitOne call for this row).
    deps.connection.writeTx((db) => {
      const notifId = createNotificationInTx(db, {
        kind: "operational",
        title: `Couldn't update Notion for ${row.taskName} — retrying`,
        body: `Couldn't update Notion for ${row.taskName} — retrying`,
        createdAt: deps.now().toISOString(),
      });
      appendOutboxInTx(db, { topic: "notification", entityId: notifId });
    });
  }
  markCommittedNotionPending(deps.connection, row.id, row.completedAt);
}

/**
 * The one commit sweep: due pending records (their undo window has
 * elapsed) and Notion-sync-pending records (already logged, Notion write
 * still owed) — both go through `commitOne`, which is a no-op re: the log
 * for a row that's already `committedAt`-marked. Called by
 * `shell/server.ts`'s commit timer AND its own startup sweep.
 */
export async function commitDueCheckOffs(deps: CheckOffDeps): Promise<void> {
  const now = deps.now();
  for (const row of listDuePendingCheckOffs(deps.connection, now)) {
    await commitOne(deps, row);
  }
  for (const row of listNotionRetryCheckOffs(deps.connection)) {
    await commitOne(deps, row);
  }
}
```

```ts
export interface CheckOffCommitTimerOptions {
  readonly intervalMs?: number;
  readonly setIntervalFn?: typeof setInterval;
  readonly clearIntervalFn?: typeof clearInterval;

export function startCheckOffCommitTimer(deps: CheckOffDeps, options: CheckOffCommitTimerOptions = {}): { stop(): void } {
  const intervalMs = options.intervalMs ?? CHECK_OFF_COMMIT_TICK_MS;
  const setIntervalFn = options.setIntervalFn ?? setInterval;
  const clearIntervalFn = options.clearIntervalFn ?? clearInterval;
  const handle = setIntervalFn(() => void commitDueCheckOffs(deps), intervalMs);

}
```

```tsx
/**
 * web/src/components/PlanChecklist.tsx — Story 7.10.
 *
 * Owns per-row optimistic check state and exactly one visible Undo Toast
 * (UX OQ7): each check-off gets its own independent pending record
 * server-side, but only the newest is shown — an earlier one's row stays
 * dissolved and commits silently once superseded.
 */
import { useState } from "react";
import type { HomePlanRow } from "../../../src/types/api.ts";
import { Checkbox } from "./Checkbox.tsx";
import { UndoToast } from "./UndoToast.tsx";
import { requestCheckOff } from "../lib/checkOffClient.ts";
import { useReducedMotion } from "../hooks/useReducedMotion.ts";

export function PlanChecklist({ rows }: { readonly rows: readonly HomePlanRow[] }): React.JSX.Element {
  const [locallyChecked, setLocallyChecked] = useState<Set<string>>(new Set());
  const [toast, setToast] = useState<{ id: string; taskId: string; taskName: string } | null>(null);
  const reducedMotion = useReducedMotion();

  const handleCheck = async (row: HomePlanRow): Promise<void> => {
    setLocallyChecked((prev) => new Set(prev).add(row.taskId));
    const { id } = await requestCheckOff(row.taskId);
    setToast({ id, taskId: row.taskId, taskName: row.label });
  };

  const handleUndo = (): void => {
    if (!toast) return;
    setLocallyChecked((prev) => {
      const next = new Set(prev);
      next.delete(toast.taskId);
      return next;
    });
    setToast(null);
  };

  return (
    <div className="flex flex-col gap-2">
      {rows.map((row) => {
        const checked = row.completed || locallyChecked.has(row.taskId);
        return (
          <div
            key={row.blockId}
            data-testid={`plan-row-${row.taskId}`}
            aria-disabled={row.past || checked}
            className={`flex items-center gap-2 rounded-md bg-surface-raised px-3 py-2 font-body text-ink-primary ${checked ? `line-through opacity-50 ${reducedMotion ? "hidden" : "transition-opacity"}` : ""} ${row.past && !checked ? "opacity-70" : ""}`}
          >
            <Checkbox label={row.label} checked={checked} disabled={checked || row.past} onCheck={() => void handleCheck(row)} />
            {row.label}
          </div>
        );
      })}
      {toast && <UndoToast id={toast.id} taskName={toast.taskName} onUndo={handleUndo} />}
    </div>
  );
}
```
