# Story 8.8 — Chat Bubble on Home and the Three-Action Capture Flow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Home gets a docked, always-focusable Chat Bubble (glass pill, "/" chip, expands on hover/focus) that sends its typed text as the first turn of a new Chat conversation and never adds a click to that path. A free-text Task description ("Lab report draft, due Thursday") — which none of the existing deterministic recognizers match — is detected by a new `detectTaskCapture` classifier and routed through the *existing* FR-26 create-path (draft → confirm → write), never a shortcut. The confirm question leads with a pre-focused "Create" chip so Enter alone confirms it. A Playwright smoke proves the whole flow — fresh launch to a focused bubble to a created Task — takes at most three actions and passes through no login/picker/extra screen; this spec is the permanent NFR-CaptureSpeed regression gate.

**Architecture:** This story adds no new persisted state and no new wire shape. It is glue across three existing seams: (1) `llm-adapter.ts` gains one more narrow, structured-extraction classifier (`detectTaskCapture`), following exactly the shape `classifyChatIntent`/`draftCalendarEditRequest` already use (an injectable client, one system prompt, a strict response grammar, fail-closed to `undefined`); (2) `app/chat-turn.ts`'s dispatch chain gains one more check, inserted after every deterministic recognizer and before the `classifyChatIntent` branch, so a capture hit is exactly as cheap (one extra LLM call, only on a line every earlier check already rejected) as the existing AD-14 search-trigger discipline; (3) `app/create-item.ts`'s `draftItem` — already the FR-26 draft → `openProposal` → (later) `confirmProposal` pipeline — gets a second caller (the capture path, database `"Tasks"`) and a small, generic improvement: every `notion-page-draft` confirm question now leads with "Create"/"Cancel" instead of a bare "Yes"/"No", because "did you want me to create this" reads oddly as a Yes/No question. `web/` adds one new component (`ChatBubble.tsx`, Home-only, reusing `chatStore.send` and `PageNavigationContext.goTo` exactly the way `NotificationOverlay.tsx`'s deep-link click already does) and one small, generally-useful addition to `StructuredQuestion.tsx` (auto-focus the first chip when a *new* question mounts) rather than a capture-flow-specific special case.

**Tech Stack:** existing `@anthropic-ai/sdk` conventions (`AnthropicMessagesClient`, `node:test` with a fake client) for the classifier; React + `useSyncExternalStore`-backed stores client-side; Playwright against `tests/e2e/fixture-server.ts` (fake Notion + fake LLM, no real network) for the end-to-end capture-flow smoke.

**Spec:** `_bmad-output/planning-artifacts/architecture/architecture-YohV1-2026-08-22/ARCHITECTURE-SPINE.md` (AD-1, AD-3, AD-12, AD-14, AD-16, AD-17); `epics.md` "## Epic 8", Story 8.8 (UX-DR35, UX-DR38, UX-DR40); SDD plan `_bmad-output/implementation-artifacts/sdd-plan-YohV1-phase2-epic8.md`, Task 9.

## Review Focus

Five failure modes the ACs imply that no single step's test would catch by accident — each gets an explicit pinning test in the step named:

1. **A genuine question must never be captured as a Task.** "What's my next meeting?" or "Why is Draft the memo prioritized?" must fall through to `classifyChatIntent`/existing recognizers, not `draftItem`. Pinned in Task 2, Step 1 (`detectTaskCapture` unit tests) and Task 2, Step 3 (`chatTurn` dispatch test with a question).
2. **An ordinary statement/status update must never be captured.** "That lecture ran long today" is neither a question nor a Task — pinned in Task 2, Step 1 and Step 3.
3. **The capture path must produce the SAME receipt/write guarantees as the explicit `parseCreateItemCommand` path** — no shortcut write, same `openProposal`/`confirmProposal` pipeline, same staleness rule. Pinned in Task 2, Step 3 (asserts `draftItem` is called, not a direct `createPage`) and Task 5's Playwright spec (asserts the Task exists in Notion only *after* confirming, never before).
4. **The "Create" chip must be the one that's pre-focused, not merely first in array order** — a re-render (e.g. a re-fetch of open items after an unrelated turn) must not silently steal focus away mid-way through Spencer reading the draft. Pinned in Task 4 (auto-focus keyed by `requestId:questionId`, re-render with the same key does NOT refocus).
5. **The bubble must be focusable before Home's own data has loaded** (it must not wait on the `"home-data"` gate, and must not register a gate of its own that could delay the launch splash). Pinned in Task 3, Step 1 (renders and is focusable synchronously, independent of `useHomeView`'s `"loading"` state) and Task 5's Playwright spec (focuses the bubble immediately after `page.goto("/")`, before waiting for any Home content).

```ts
// ============================================================================
// detectTaskCapture (Story 8.8 / FR-26 extended, AD-14's cost discipline) —
// chat-turn.ts calls this ONLY after every deterministic recognizer
// (time-budget, plan-view, mid-day-reflow, blocker, why-prioritized,
// save-search-result, create-item's explicit Notion mention, calendar-edit)
// has already failed to match — never on every message unconditionally.
// It answers one question only: "does this line describe something Spencer
// wants tracked as a new Task?" It does NOT draft the Task's fields itself
// — a hit is hened off to the existing draftNotionPageFields/createPage
// pipeline via app/create-item.ts's draftItem, unchanged, so a captured
// Task goes through the exact same confirm-then-write trust boundary as an
// explicit "create a task ..." command.
// ============================================================================

const DETECT_TASK_CAPTURE_MAX_TOKENS = 16;

const DETECT_TASK_CAPTURE_SYSTEM_PROMPT = [
  "You are Yoh's task-capture detector. Decide whether Spencer's message describes something he needs to DO or produce later — a new Task he wants tracked (an assignment, an errand, a chore, a deliverable, with or without a stated due date) — as opposed to a question he's asking, a status update, or ordinary conversation.",
  "If it clearly describes a new Task to track, respond with exactly: CAPTURE",
  "Otherwise (a question, a greeting, a status update, small talk, or anything ambiguous) respond with exactly: NONE",
].join("\n");

/**
 * Returns `{request: line}` (the ONE input `app/create-item.ts`'s
 * `draftItem` needs — the same shape `parseCreateItemCommand` already
 * returns as `.request`) when Claude confidently says `line` describes a
 * new Task, else `undefined`. Never throws for "not a capture" — only a
 * genuine API/transport failure propagates (AD-8), exactly like
 * `classifyChatIntent`/`draftCalendarEditRequest` above.
 */
export async function detectTaskCapture(
  client: AnthropicMessagesClient,
  line: string,
): Promise<{ readonly request: string } | undefined> {
  const message = await client.messages.create({
    model: CLAUDE_CHAT_MODEL_FAST,
    max_tokens: DETECT_TASK_CAPTURE_MAX_TOKENS,
    system: DETECT_TASK_CAPTURE_SYSTEM_PROMPT,
    messages: [{ role: "user", content: line }],
  });

  const text = message.content
    .filter((block): block is Anthropic.TextBlock => block.type === "text")
    .map((block) => block.text)
    .join("\n")
    .trim();

  return /^CAPTURE\b/i.test(text) ? { request: line } : undefined;
}
```

```tsx
/**
 * web/src/components/ChatBubble.tsx
 *
 * Story 8.8, UX-DR35, DESIGN.md `chat-bubble`: Home's always-available
 * capture surface. A glass pill, small and centered when collapsed,
 * expanding wide on hover or focus with a 2px accent-solid focus ring plus
 * accent-glow (DESIGN.md's exact `chat-bubble.focus` value). Enter sends
 * the typed text as the first turn of a new Chat conversation and moves to
 * Chat (FR-40) — the SAME `chatStore.send` the Chat page's own Chat Input
 * calls (Task 6), so there is exactly one send path. "/" opens the Command
 * Palette in place (Task 8's palette, mounted directly under this pill).
 * Esc collapses it. It registers NO readiness gate — Home's "home-data"
 * gate (Story 7.8, Ruling R16) stays the only one — and is focusable the
 * instant it mounts, independent of Home's own fetch (FR-39,
 * NFR-CaptureSpeed): this component takes no props from HomePage's
 * `useHomeView()` state at all.
 */
import { useRef, useState } from "react";
import { PAGES } from "../lib/pages.ts";
import { usePageNavigationContext } from "../lib/navigationContext.tsx";
import { send, setDraft, useChatDraft } from "../lib/chatStore.ts";
import { CommandPalette } from "./CommandPalette.tsx";

const CHAT_PAGE_INDEX = PAGES.findIndex((p) => p.id === "chat");

export function ChatBubble(): React.JSX.Element {
  const nav = usePageNavigationContext();
  const draft = useChatDraft();
  const [expanded, setExpanded] = useState(false);
  const inputRef = useRef<HTMLInputElement>(null);
  const paletteOpen = draft.startsWith("/");

  const collapse = (): void => {
    setExpanded(false);
    inputRef.current?.blur();
  };

  const submit = (): void => {
    const message = draft.trim();
    if (message.length === 0) return;
    send(message);
    setDraft("");
    nav.goTo(CHAT_PAGE_INDEX);
  };

  const handleKeyDown = (e: React.KeyboardEvent<HTMLInputElement>): void => {
    if (e.key === "Escape") {
      e.preventDefault();
      collapse();
      return;
    }
    if (e.key === "Enter" && !paletteOpen) {
      e.preventDefault();
      submit();
    }
  };

  return (
    <div
      data-testid="chat-bubble"
      className={
        "chat-glass pointer-events-auto absolute bottom-5 left-1/2 -translate-x-1/2 rounded-full font-body text-body text-ink-primary transition-[width] focus-within:shadow-[0_0_0_var(--focus-ring-width)_var(--color-accent-solid),0_0_16px_var(--color-accent-glow)] " +
        (expanded ? "w-[min(32rem,90vw)]" : "w-64")
      }
    >
      <div className="flex items-center gap-2 px-4 py-2.5">
        <span aria-hidden="true" className="rounded-sm bg-surface-sunken px-1.5 py-0.5 text-caption text-ink-secondary">
          /
        </span>
        <input
          ref={inputRef}
          type="text"
          aria-label="Ask Yoh, or type / for commands"
          placeholder="Ask Yoh, or type / for commands"
          value={draft}
          onFocus={() => setExpanded(true)}
          onBlur={() => {
            if (draft.trim().length === 0) setExpanded(false);
          }}
          onChange={(e) => setDraft(e.target.value)}
          onKeyDown={handleKeyDown}
          className="w-full bg-transparent font-body text-body text-ink-primary placeholder:text-ink-secondary focus:outline-none"
        />
      </div>
      {paletteOpen && (
        <CommandPalette
          query={draft}
          onClose={() => setDraft("")}
          onRun={(message) => {
            send(message);
            setDraft("");
            nav.goTo(CHAT_PAGE_INDEX);
          }}
        />
      )}
    </div>
  );
}
```

```ts
import { test, expect } from "@playwright/test";

// Story 8.8's permanent NFR-CaptureSpeed regression gate: from a fresh
// launch, no login/picker/extra screen appears before a focused Chat
// Bubble, and sending a captured Task takes at most three actions
// (focus/click the bubble, type, Enter). Runs against
// tests/e2e/fixture-server.ts's fake LLM + fake Notion — no real network.

test("fresh launch shows a focused-reachable Chat Bubble with no login, picker, or extra screen first", async ({ page }) => {
  await page.goto("/");
  // Action 1: focus the bubble.
  const input = page.getByRole("textbox", { name: /ask yoh, or type \/ for commands/i });
  await input.click();
  await expect(input).toBeFocused();
  // No modal/dialog of any kind stood between launch and this focus.
  expect(await page.locator('[role="dialog"], [role="alertdialog"]').count()).toBe(0);
});

test("capture -> confirm -> receipt: three actions get a Task drafted and created", async ({ page }) => {
  await page.goto("/");
  const input = page.getByRole("textbox", { name: /ask yoh, or type \/ for commands/i });

  // Action 1: focus.
  await input.click();
  // Action 2: type.
  await input.fill("Lab report draft, due Thursday");
  // Action 3: Enter — sends AND navigates to Chat, per FR-40/UX-DR35.
  await input.press("Enter");

  await expect(page.getByText(/Here's what I'll create in Tasks/)).toBeVisible();

  // The FR-26 confirm-then-write trust boundary: the Task must not exist
  // in Notion yet, only the draft is shown.
  const preConfirm = await (await page.request.get("/__fixture/state?taskId=x")).json();
  expect(preConfirm.createdPages).toEqual([]);

  // The "Create" chip is pre-focused (Story 8.8 AC3) — Enter alone confirms it.
  const createChip = page.getByRole("button", { name: "Create" });
  await expect(createChip).toBeFocused();
  await page.keyboard.press("Enter");

  await expect(page.getByText(/Created "Lab report draft" in Tasks/)).toBeVisible();
  await expect
    .poll(async () => (await (await page.request.get("/__fixture/state?taskId=x")).json()).createdPages)
    .toEqual([{ title: "Lab report draft" }]);
});

test("a genuine question is never captured as a Task", async ({ page }) => {
  await page.goto("/");
  const input = page.getByRole("textbox", { name: /ask yoh, or type \/ for commands/i });
  await input.click();
  await input.fill("What's my next meeting?");
  await input.press("Enter");
  await expect(page.getByText(/Here's what I'll create/)).toHaveCount(0);
});
```
