# Story 9.2 — /sandbox Card Flow — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Spencer types `/sandbox` in Chat and is walked, one Sandbox Card at a time, through every Task missing a Required field (Due Date and/or Estimated Duration only, post-Task-1) — soonest-due first, no-due-date last — with a live "N remaining" count. Each card lets him fill Due Date/Estimated Duration (required, rimmed) and optionally Area/Energy; **Save** writes synchronously through the existing `updateTaskField` binder as a direct write (no confirm step, no `Proposal`, FR-38/AD-12), validating every provided field before writing any of them so a bad guess writes nothing; **Skip** writes nothing and leaves the Task eligible for the next session. The next card appears below; earlier cards (saved, skipped, or mid-edit) stay visible in the same chat stream. An empty queue gets a plain, honest reply and the session ends with no finale (Task 3's concern). `app/sandbox-queue.ts`'s `sandboxQueue` is the **one** computed source for this count — no consumer (this story's card flow, Task 4's Needs-Data Indicator, Task 4's `needs-data` notification) ever keeps its own.

**Architecture:** `sandboxQueue` (new, `app/sandbox-queue.ts`) is a pure-ish orchestration function in the same family as `rituals/data-completeness.ts`'s `runDataCompletenessGate`: it reads live Tasks, merges any stored `TaskFieldOverride`s via `rituals/data-completeness.ts`'s existing `mergeStoredOverrides` (`app/` → `rituals/` is a permitted edge, precedent: `app/night-close-out.ts` importing `rituals/night-ritual.ts`), runs Task 1's reshaped `checkDataCompleteness` (which, post-Task-1, reports `incomplete` over Required fields only — a Task missing only Area/Energy never appears there at all), and maps its `incomplete` list into `SandboxQueueItem`s, sorted soonest-due-first with no-due-date last, minus anything in `input.exclude`. `submitSandboxCard` (new, `app/sandbox-submit.ts`) validates every provided field through `core/planning-field-value.ts`'s `parsePlanningFieldValue` *before* writing any of them — Area and Energy's live-schema select-guard resolution happens *inside* `updateTaskField` itself (`writeSelectLikeField`, `notion-adapter.ts`) on the same call that performs the write, so there is no separate "resolve only" step to call ahead of time; this plan's own judgment call (documented in Task 2 below) writes Area/Energy **before** Due Date/Estimated Duration specifically so the one field kind that can fail its live-schema check is always attempted first, minimizing (but not eliminating — Notion has no cross-field transaction) how often a bad guess leaves an earlier field already committed. `/sandbox`'s *first* card reaches Chat through the **existing** `chatTurn` dispatch (`app/chat-turn.ts`'s `dispatchSlashCommand`, Story 8.7) — no new route for it — as an additive `ChatTurnResponse.sandboxCard` field; every subsequent card comes from `next` on a save/skip response, over three new routes (`POST /api/sandbox/start|:taskId/save|:taskId/skip`) that are pure transport over `sandboxQueue`/`submitSandboxCard`, mirroring `src/shell/server.ts`'s existing Tasks-page route shape (`validator("json"/"query", ...)`, a `deps.sandbox` optional bucket + one shared `SANDBOX_NOT_CONFIGURED` envelope, exactly like `deps.tasks`/`TASKS_NOT_CONFIGURED`). Client-side, `web/src/lib/chatStore.ts`'s `ChatStoreState.messages: readonly ChatViewMessage[]` becomes `entries: readonly StreamEntry[]` — a discriminated union of `{kind:"message"; id; message: ChatViewMessage}` and `{kind:"sandbox-card"; id; view: SandboxCardView; status; receipt?}`, each carrying its own `id` so one small pair of generic helpers (`appendStreamEntry`/`updateStreamEntry`) can add and settle *any* future stream-entry kind (Task 3's own `"sandbox-finale"` kind reuses these verbatim) without a bespoke append/patch function per kind. `web/src/lib/sandbox.ts` (new) is the session's own bookkeeping — `{card, exclude, outcomes}` behind a `useSyncExternalStore` store, the same shape family as `chatStore.ts`/`chatPanel.ts` — plus the actual network calls, over a new thin `web/src/lib/sandboxClient.ts` (mirrors `checkOff.ts`'s exact `settle<T>` outcome-wrapper convention: a rejected request and an `{ok:false}` envelope both resolve to `{ok:false, message}`, never a throw). `web/src/components/SandboxCard.tsx` (new) renders one `"sandbox-card"` `StreamEntry`; `ChatPanel.tsx`'s stream loop switches on `entry.kind` to render either `<ChatMessage>` or `<SandboxCard>`, so a card genuinely interleaves with ordinary turns in one ordered list, matching "the next card appears below; earlier cards stay in chat history."

**Tech Stack:** `node:test` with fake adapters (`tests/fakes/fake-notion-tasks-db.ts`, extended with one more fixture Task) for `src/`; Vitest + RTL for `web/` units; Playwright (`web/e2e/sandbox.spec.ts`, new) against `tests/e2e/fixture-server.ts`, extended with a `deps.sandbox` wiring and one dedicated fixture Task missing both Required fields. No new npm packages.

**Spec:** `_bmad-output/planning-artifacts/architecture/architecture-YohV1-2026-08-22/ARCHITECTURE-SPINE.md` AD-1, AD-2, AD-3, AD-5, AD-8, AD-9, AD-11, AD-12, AD-16, AD-17, AD-18; `_bmad-output/planning-artifacts/epics.md` Story 9.2 (FR-36, FR-37, FR-38); `_bmad-output/planning-artifacts/ux-designs/ux-YohV1-2026-08-21/DESIGN.md`/`EXPERIENCE.md` UX-DR39 (Sandbox Card); `_bmad-output/implementation-artifacts/sdd-plan-YohV1-phase2-epic9.md` Task 2 (Epic 9 Interface Contract E5–E7, E9–E10; Task 2's own Owns/Implementer-notes/controller rulings/ACs).

## Assumptions about earlier tasks

Task 1 (Story 9.1: `Refining<T>`, `RequiredFieldNames`, `RefiningFieldNames`, the reshaped `CompleteTask`/`checkDataCompleteness`/`MissingFieldReport` in `types/domain.ts`/`core/data-completeness-gate.ts`) does not exist in the repository yet. Everything below is built directly against the SDD plan's own Epic 9 Interface Contract (E1–E4), quoted verbatim where it binds; where the contract is silent this plan states its assumption so the controller can correct it at dispatch time if Task 1 lands differently. This plan also aligns, wherever the two plans touch the same file, with the **already-written** `docs/superpowers/plans/2026-09-27-story-9.3-sandbox-finale-and-proof-of-action-notification.md` (Task 3's own plan, found already present in `docs/superpowers/plans/` while writing this one) — its own "Assumptions about earlier tasks" section guesses at several of this story's shapes, and this plan adopts those guesses verbatim wherever they are reasonable, to minimize cross-plan rework:

1. **`checkDataCompleteness(tasks: readonly Task[])`'s signature is unchanged by Task 1** — only what it considers changes (E2: "computes missingness over `RequiredFieldNames` only"). This plan's `sandboxQueue` calls it exactly as `rituals/data-completeness.ts`'s `runDataCompletenessGate` does today, and reads only `result.value.incomplete` (never `completeTasks`, so this file never touches `Refining<T>` unwrapping at all — that is `derived-priority.ts`'s concern, untouched by this story).
2. **`MissingFieldReport.missingFields` narrows to `readonly RequiredFieldNames[]`** (E2, verbatim) — `SandboxQueueItem.missingFields` is typed identically, with no cast needed beyond importing the new alias.
3. **`RequiredFieldNames = "dueDate" | "estimatedDurationMinutes"`** (E1, verbatim) — this is the only place this plan imports it from `types/domain.ts`.
4. **A Task missing only Area and/or Energy never appears in `incomplete`** (E2: "not reported in `incomplete` at all... fully eligible") — this is precisely what makes FR-36 ("Tasks missing only Refining Fields are not queued") true for free, once Task 1 lands; this plan's own tests pin it by constructing a Task missing only Area (never Due Date/Duration) and asserting it is absent from `sandboxQueue`'s `items`.
5. **`SandboxSubmitDeps` (this story's own new type, `src/app/sandbox-submit.ts`) is shared with Task 3's `finishSandboxSession`.** Task 3's plan assumed a superset including `store: MemoryStore`; this plan's own `submitSandboxCard` never reads `store` (a Sandbox Card write touches only Notion + the outbox, never `memory-store.ts` — Sandbox Cards are explicitly not Structured Questions, SDD Global Constraints), so `store` is **left out** of the real `SandboxSubmitDeps` below. `connection: SqliteConnection` and `now: () => Date` **are** included as required fields (matching Task 3's assumption exactly, even though `submitSandboxCard` itself only reads `connection`, never `now`) so Task 3's `finishSandboxSession(deps: SandboxSubmitDeps, ...)` compiles against the same object unmodified. Flagging this precisely for whichever implementer builds Task 3: `deps.store` is not part of this type; if Task 3's own body ends up needing it after all, it is an easy additive widen, not a breaking one.
6. **`ServerDeps.sandbox` and `SANDBOX_NOT_CONFIGURED`** — this plan builds the real bucket and constant Task 3's plan assumed by name (`SANDBOX_NOT_CONFIGURED`, an optional `deps.sandbox` object carrying `readTasks`/`updateTaskField`/`timeZone`/optional `now`). Task 3 adds one more route (`POST /api/sandbox/finish`) reading the exact same bucket.
7. **`chatStore.ts`'s `StreamEntry` union and its generic `appendStreamEntry`/`updateStreamEntry` helpers** — this plan implements the two generic helpers exactly as Task 3's plan assumed them (`appendStreamEntry(entry): string`, `updateStreamEntry(id, patch): void`), rather than kind-specific append/patch functions, precisely so Task 3's own `"sandbox-finale"` kind (and any later kind) reuses them verbatim. The contract's (E10) own shorthand `{kind:"message"; turn: ChatTurn}` is read as descriptive, not literal: this plan's `"message"` variant instead wraps the existing, richer `ChatViewMessage` (which already carries `statusText`/`errorText`/`receipts`/`question` — fields a bare `{role, content}` `ChatTurn` cannot hold, and `ChatMessage.tsx` already depends on). This is flagged here as a deliberate, judgment-call reshaping of E10's own wording, not a silent deviation — if the controller wants the literal `ChatTurn` shape instead, only `chatStore.ts`'s `"message"` arm and its two or three internal call sites need to change; every other file in this plan is unaffected.
8. **`web/src/lib/sandboxClient.ts` (new, this plan's own naming, matching Task 3's Assumption #5 exactly)** — mirrors `web/src/lib/checkOff.ts`'s `settle<T>`/`CheckOffOutcome<T>` convention verbatim, renamed `SandboxOutcomeResult<T>` (Task 3's own assumed name). `web/src/lib/sandbox.ts` calls through this file rather than calling `apiClient` directly, so Task 3's own `requestSandboxFinish` sits beside these three as a natural sibling export.

## Global Constraints

The subset binding this story (full text: SDD plan's "Global Constraints" section):

- **Layering (AD-1):** `app/sandbox-queue.ts`/`app/sandbox-submit.ts` import only `types/`, other `core/`/`app/`, and (permitted) `rituals/data-completeness.ts` for `mergeStoredOverrides` — never `shell/`. `web/` imports only `import type` from `src/types/`.
- **`app/` layer (AD-16):** `sandboxQueue`/`submitSandboxCard` are each `(deps, input) => Promise<Result<Output, YohError>>`; every exported interface/type is exempt.
- **Functional core / Result (AD-2, AD-8):** neither function throws; every adapter call is wrapped and converted.
- **Propose-Don't-Impose (AD-3):** unaffected — a Sandbox Card write is FR-38's own direct-write tier (AD-12 amended), never a `Proposal`, never routed through `confirm-proposal.ts`.
- **Sandbox Cards are not Structured Questions (Epic 9 specifics):** `submitSandboxCard`/`sandboxQueue` never touch `memory-store.ts`'s `interaction-request` table, never go through `answer-open-item.ts`/`confirm-proposal.ts`, and are not surfaced by `surface-open-items.ts`.
- **The one computed source (AD-11, E5):** `sandboxQueue` is the only function that derives the queue; this story's own card flow calls it, never a parallel count.
- **Direct writes (FR-38, AD-12 amended):** `submitSandboxCard` writes through the exact same `NotionTaskWriteBindings.updateTaskField` binder `app/update-task.ts` already uses — no new Notion call shape, no second confirmation.
- **Storage (AD-10, AD-18):** a successful save appends exactly one `tasks`-topic outbox hint via `appendOutboxInTx`, same pattern as `update-task.ts`'s own `hint()`.
- **Browser client (AD-17):** every queue item, "N remaining" count, and disabled/validation rule is computed server-side; the client's own Save-disabled-until-both-Required-fields-filled check is a UX convenience only, re-checked server-side regardless.
- **Web UI (FR-46, NFR-Accessibility):** `SandboxCard.tsx` uses only `web/src/tokens.css` tokens; its save-pulse animation reads `useReducedMotion.ts` and has an instant ("Saved" text only) fallback; the counter uses tabular numerals; nothing is conveyed by color alone.
- **Tone (FR-18, FR-19, FR-42):** the empty-queue reply and every field-validation message are plain, peer-level sentences, no filler.
- **Tests:** `node:test` for `src/`, Vitest + RTL for `web/`, Playwright smoke for `web/`. Gate: `npm run check` plus `cd web && npx playwright test`. Baseline at this plan's dispatch (post-Task-1, pre-this-story): node/web/Playwright counts are whatever Task 1 leaves them at — this plan's own gate step re-reads the counts freshly rather than restating a stale baseline.
- **Process:** one squashed commit, `feat(9.2): /sandbox card flow`, with `sprint-status.yaml`'s `9-2-sandbox-card-flow` key set to `done` in the same commit. Commit trailer is exactly `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

Five failure modes the ACs imply but no single step, by itself, already pins — each gets its own test in the step named:

1. **A card with a bad Area or Energy writes nothing at all, even when Due Date and Estimated Duration parsed fine** ("an unresolvable value re-prompts on that card and writes nothing" reads whole-card, not per-field). Pinned in Task 2, Step 1 (`sandbox-submit.test.ts`, a fake `updateTaskField` that accepts `dueDate`/`estimatedDurationMinutes` but rejects `area`, asserting `updateTaskField` is never even called for the two Required fields once Area is attempted first and fails).
2. **A Task missing only Area and/or Energy (no Required field missing) never appears in `sandboxQueue`'s `items`**, even though it would have under the pre-Task-1 all-five-fields gate (FR-36; this is the one place this story's own tests must prove Task 1's reshape actually reaches `/sandbox`, not just `core/data-completeness-gate.ts`'s own suite). Pinned in Task 1, Step 1 (`sandbox-queue.test.ts`).
3. **Skip never calls `updateTaskField` and never appends an outbox hint** — a source-scan test (this codebase's own established convention, mirroring `tests/layering-rules.test.ts`/the FR-29 isolation test in `docs/superpowers/plans/2026-09-26-story-8.2-one-confirmation-path.md`) proving `POST /api/sandbox/:taskId/skip`'s own route handler body never names `submitSandboxCard` or `updateTaskField`. Pinned in Task 5, Step 1 (`server-sandbox.test.ts`).
4. **The client's `exclude` set accumulates BOTH saved and skipped taskIds this session** (deliberate: guards against Notion read-after-write staleness reintroducing a just-saved Task at the top of the very next `sandboxQueue` call). Pinned in Task 7, Step 1 (`sandbox.test.ts`).
5. **An empty queue at `/sandbox` time returns `sandboxCard: undefined` on the `ChatTurnResponse`, never an empty/zero-remaining card object** — a client that ever fell back to "falsy card" instead of "field absent" would render a broken empty card rather than nothing. Pinned in Task 4, Step 1 (`app-chat-turn.test.ts`, asserting the response has no `sandboxCard` key at all via `"sandboxCard" in result.value`, not just a falsy check).

/**
 * src/app/sandbox-queue.ts
 *
 * Story 9.2 (AD-11, E5): the ONE computed source for `/sandbox`'s queue —
 * re-derives it from a live Notion read plus the Data-Completeness Gate
 * every time it's called. No new SQLite table, no new `InteractionRequest`
 * kind, no stored count anywhere. Every consumer (this story's card flow,
 * Task 4's Needs-Data Indicator, Task 4's `needs-data` notification count)
 * calls this function directly — none keeps its own count.
 *
 * Reuses `rituals/data-completeness.ts`'s `mergeStoredOverrides` (`app/` ->
 * `rituals/` is a permitted edge, precedent: `app/night-close-out.ts`
 * importing `rituals/night-ritual.ts`) rather than duplicating that merge
 * logic — a previously-answered field (through the blind FR-4 ask, or a
 * prior Sandbox Card save) counts here exactly as it does for the Morning
 * Plan.
 */
import { mergeStoredOverrides } from "../rituals/data-completeness.ts";
import { checkDataCompleteness } from "../core/data-completeness-gate.ts";
import { errorCopyForThrown } from "../core/error-copy.ts";
import type { LogEntry } from "../adapters/logger.ts";
import type { MemoryStore } from "../adapters/memory-store.ts";
import type { SandboxCardView } from "../types/api.ts";
import type { Energy, IsoDate, RequiredFieldNames, Result, Task, YohError } from "../types/domain.ts";

export interface SandboxQueueItem {
  readonly taskId: string;
  readonly taskTitle: string;
  readonly dueDate?: IsoDate;
  readonly estimatedDurationMinutes?: number;
  readonly area?: string;
  readonly energy?: Energy;
  /** Always non-empty — which Required field(s) this Task is missing. */
  readonly missingFields: readonly RequiredFieldNames[];
}

export interface SandboxQueueDeps {
  readonly store: MemoryStore;
  readonly readTasks: () => Promise<readonly Task[]>;
  readonly now: () => Date;
  readonly timeZone: string;
  readonly log?: (entry: LogEntry) => void;
}

export interface SandboxQueueInput {
  /** taskIds to leave out — the CURRENT `/sandbox` session's already-handled cards. Omitted/`[]` for the "true" global count. */
  readonly exclude?: readonly string[];
}

export interface SandboxQueueResponse {
  readonly items: readonly SandboxQueueItem[];
}

/** Soonest-due-first; no-due-date last; ties broken by title (stable, locale-independent). */
function compareItems(a: SandboxQueueItem, b: SandboxQueueItem): number {
  if (a.dueDate === undefined && b.dueDate === undefined) return a.taskTitle < b.taskTitle ? -1 : a.taskTitle > b.taskTitle ? 1 : 0;
  if (a.dueDate === undefined) return 1;
  if (b.dueDate === undefined) return -1;
  if (a.dueDate !== b.dueDate) return a.dueDate < b.dueDate ? -1 : 1;
  return a.taskTitle < b.taskTitle ? -1 : a.taskTitle > b.taskTitle ? 1 : 0;
}

export async function sandboxQueue(deps: SandboxQueueDeps, input: SandboxQueueInput): Promise<Result<SandboxQueueResponse, YohError>> {
  let tasks: readonly Task[];
  try {
    tasks = await deps.readTasks();
  } catch (err) {
    return { ok: false, error: { kind: "unreachable", message: errorCopyForThrown(err, { service: "Notion" }) } };
  }

  const merged = mergeStoredOverrides(deps.store, tasks);
  const gated = checkDataCompleteness(merged);
  if (!gated.ok) return gated;

  const exclude = new Set(input.exclude ?? []);
  const byId = new Map(merged.map((t) => [t.id, t] as const));

  const items: SandboxQueueItem[] = gated.value.incomplete
    .filter((report) => !exclude.has(report.taskId))
    .map((report) => {
      const task = byId.get(report.taskId);
      return {
        taskId: report.taskId,
        taskTitle: report.taskTitle,
        ...(task?.dueDate !== undefined ? { dueDate: task.dueDate } : {}),
        ...(task?.estimatedDurationMinutes !== undefined ? { estimatedDurationMinutes: task.estimatedDurationMinutes } : {}),
        ...(task?.area !== undefined ? { area: task.area } : {}),
        ...(task?.energy !== undefined ? { energy: task.energy } : {}),
        missingFields: report.missingFields,
      };
    })
    .sort(compareItems);

  return { ok: true, value: { items } };
}

/**
 * The shared "first item -> wire view" step every caller needs identically
 * (`app/chat-turn.ts`'s `/sandbox` dispatch, and `shell/server.ts`'s three
 * routes) — not in E5's own list, but explicitly allowed ("a task may add
 * fields or helpers"). `remaining` is what the card itself shows as "N
 * remaining" — the queue's length AFTER this card (E7).
 */
export function firstCardView(items: readonly SandboxQueueItem[]): SandboxCardView | undefined {
  const [first, ...rest] = items;
  if (!first) return undefined;
  return { ...first, remaining: rest.length };
}

## Task 2: `app/sandbox-submit.ts` — `submitSandboxCard`

**Files:** New `src/app/sandbox-submit.ts`, `tests/sandbox-submit.test.ts`.

**Interfaces:** Consumes `parsePlanningFieldValue`/`PLANNING_FIELD_LABELS` (`core/planning-field-value.ts`), `appendOutboxInTx` (`adapters/notification-store.ts`), `TASKS_TOPIC` (`app/create-task.ts`), `NotionTaskWriteBindings["updateTaskField"]`. Produces `submitSandboxCard`, `SandboxSubmitDeps`/`SandboxCardInput`/`SandboxCardOutput` (per Interfaces above).

**A design decision, flagged for the controller:** `submitSandboxCard` writes Area and Energy (if present) **before** Due Date and Estimated Duration. Area/Energy's live-schema select-guard resolution happens *inside* the same `updateTaskField` call that performs the write (`notion-adapter.ts`'s `writeSelectLikeField` — there is no separate "resolve only, don't write yet" step to call ahead of time, and E6 explicitly forbids inventing a second guard). Due Date/Estimated Duration, once `parsePlanningFieldValue` has accepted them, essentially cannot fail their own Notion write except on a genuine network/service outage — so ordering "the field kind that can fail its live-schema check" first means the common failure case (a bad Area/Energy guess) never leaves *anything* written. This does **not** make the whole card's write atomic — Notion has no cross-field transaction, so if Area's write succeeds and Energy's *then* fails, Area is already committed even though this function reports `ok:false`. This mirrors every other multi-step Notion write in this codebase (none is transactional across fields); FR-38's "writes nothing" is read here as "no *additional* field is committed once a failure is hit," not as an atomic guarantee this codebase has never provided anywhere. If the controller wants a different ordering or an explicit two-phase validate/write split, this is the one place to change it — nothing downstream depends on the specific order.

/**
 * src/app/sandbox-submit.ts
 *
 * Story 9.2 (FR-38, AD-12 amended, E6): `submitSandboxCard` — a Sandbox
 * Card's direct write, no confirm step, no `Proposal`. Validates every
 * PROVIDED field through `core/planning-field-value.ts`'s
 * `parsePlanningFieldValue` before writing any of them; Area/Energy (if
 * present) are then written FIRST, through the exact same
 * `NotionTaskWriteBindings.updateTaskField` binder `app/update-task.ts`
 * already uses (same live-schema select-guard resolution, same rejection
 * message shape — no second guard invented), so the one field kind whose
 * write can fail on validity is always attempted before Due Date/Estimated
 * Duration (see this file's own doc comment in the per-story plan for the
 * full ordering rationale). Only once every provided field's write has
 * succeeded does this append one `tasks`-topic outbox hint (AD-18).
 *
 * Story 9.3 appends `finishSandboxSession` to this same file — the Finale's
 * one server round trip, raising the session's proof-of-action
 * notification from the client's own accumulated outcome list.
 */
import { appendOutboxInTx } from "../adapters/notification-store.ts";
import { errorCopy, errorCopyForThrown } from "../core/error-copy.ts";
import { PLANNING_FIELD_LABELS, parsePlanningFieldValue } from "../core/planning-field-value.ts";
import { TASKS_TOPIC } from "./create-task.ts";
import type { LogEntry } from "../adapters/logger.ts";
import type { SqliteConnection } from "../adapters/sqlite.ts";
import type { NotionTaskWriteBindings } from "../adapters/notion-adapter.ts";
import type { PlanningFieldNames, Result, Task, YohError } from "../types/domain.ts";

export interface SandboxSubmitDeps {
  readonly readTasks: () => Promise<readonly Task[]>;
  readonly updateTaskField: NotionTaskWriteBindings["updateTaskField"];
  readonly connection: SqliteConnection;
  /** Unused by `submitSandboxCard` itself — carried so Story 9.3's `finishSandboxSession` (this same file) shares one deps object. */
  readonly now: () => Date;
  readonly log?: (entry: LogEntry) => void;
}

export interface SandboxCardInput {
  readonly taskId: string;
  readonly dueDate: string;
  readonly estimatedDurationMinutes: string;
  readonly area?: string;
  readonly energy?: string;
}

export interface SandboxCardOutput {
  readonly taskId: string;
  readonly taskTitle: string;
  readonly receipt: string;
}

function invalid(message: string): { ok: false; error: YohError } {
  return { ok: false, error: { kind: "validation", message } };
}

/** Parses every PROVIDED field up front — nothing is written until every one of these succeeds. */
function parseAll(input: SandboxCardInput): Result<
  { readonly dueDate: string; readonly estimatedDurationMinutes: number; readonly area?: string; readonly energy?: Task["energy"] },
  YohError
> {
  const dueDate = parsePlanningFieldValue("dueDate", input.dueDate);
  if (!dueDate.ok) return invalid(dueDate.message);
  const duration = parsePlanningFieldValue("estimatedDurationMinutes", input.estimatedDurationMinutes);
  if (!duration.ok) return invalid(duration.message);

  let area: string | undefined;
  if (input.area !== undefined) {
    const parsed = parsePlanningFieldValue("area", input.area);
    if (!parsed.ok) return invalid(parsed.message);
    area = parsed.value as string;
  }
  let energy: Task["energy"] | undefined;
  if (input.energy !== undefined) {
    const parsed = parsePlanningFieldValue("energy", input.energy);
    if (!parsed.ok) return invalid(parsed.message);
    energy = parsed.value as Task["energy"];
  }

  return {
    ok: true,
    value: { dueDate: dueDate.value as string, estimatedDurationMinutes: duration.value as number, ...(area !== undefined ? { area } : {}), ...(energy !== undefined ? { energy } : {}) },
  };
}

function hint(deps: SandboxSubmitDeps, taskId: string): void {
  deps.connection.writeTx((db) => appendOutboxInTx(db, { topic: TASKS_TOPIC, entityId: taskId }));
}

export async function submitSandboxCard(deps: SandboxSubmitDeps, input: SandboxCardInput): Promise<Result<SandboxCardOutput, YohError>> {
  const parsed = parseAll(input);
  if (!parsed.ok) return parsed;

  let tasks: readonly Task[];
  try {
    tasks = await deps.readTasks();
  } catch (err) {
    return { ok: false, error: { kind: "unreachable", message: errorCopyForThrown(err, { service: "Notion" }) } };
  }
  const task = tasks.find((t) => t.id === input.taskId);
  if (!task) return invalid("That Task couldn't be found.");

  // Area/Energy first (the one write kind whose live-schema resolution can
  // fail) — see this file's own doc comment for the full ordering rationale.
  const writes: ReadonlyArray<[PlanningFieldNames, NonNullable<Task[PlanningFieldNames]>]> = [
    ...(parsed.value.area !== undefined ? ([["area", parsed.value.area]] as const) : []),
    ...(parsed.value.energy !== undefined ? ([["energy", parsed.value.energy]] as const) : []),
    ["dueDate", parsed.value.dueDate],
    ["estimatedDurationMinutes", parsed.value.estimatedDurationMinutes],
  ];

  const changed: PlanningFieldNames[] = [];
  for (const [field, value] of writes) {
    let written: Result<void, YohError>;
    try {
      written = await deps.updateTaskField(input.taskId, field, value);
    } catch (err) {
      written = { ok: false, error: { kind: "unreachable", message: errorCopyForThrown(err, { service: "Notion" }) } };
    }
    if (!written.ok) {

/**
 * web/src/lib/chatStore.ts
 *
 * Story 8.5, contract C6, extended by Story 9.2: the ONE chat transcript +
 * unsent-draft store. `ChatStoreState.entries` is a `StreamEntry` union —
 * `"message"` (an ordinary turn, unchanged `ChatViewMessage` payload) or
 * `"sandbox-card"` (a Sandbox Card rendered inline, Story 9.2) — so a card
 * genuinely interleaves with turns in one ordered stream and "stays in chat
 * history" once settled. `history` sent to the server
 * (`ChatTurnRequest.history`) is still built from `"message"` entries only —
 * a card is never appended to the LLM-facing transcript. `appendStreamEntry`/
 * `updateStreamEntry` are generic over any future `StreamEntry` kind (Story
 * 9.3 adds a `"sandbox-finale"` kind and reuses these two verbatim).
 */
import { useSyncExternalStore } from "react";
import { streamChat } from "./chatStream.ts";
import { startSandbox } from "./sandbox.ts";
import { addLocalFailureNotice } from "./notifications.ts";
import type { ChatStreamEvent, ChatTurnRequest, OpenItemQuestion, SandboxCardView } from "../../../src/types/api.ts";

export interface ChatViewMessage {
  readonly id: string;
  readonly role: "user" | "assistant";
  readonly text: string;
  readonly receipts: readonly string[];
  readonly question?: OpenItemQuestion;
  readonly status: "done" | "streaming" | "error";
  readonly statusText?: string;
  readonly errorText?: string;
}

export type StreamEntry =
  | { readonly kind: "message"; readonly id: string; readonly message: ChatViewMessage }
  | {
      readonly kind: "sandbox-card";
      readonly id: string;
      readonly view: SandboxCardView;
      readonly status: "pending" | "saved" | "skipped" | "failed";
      readonly receipt?: string;
    };

export interface ChatStoreState {
  readonly entries: readonly StreamEntry[];
  readonly draft: string;
  readonly sending: boolean;
}

const INITIAL_STATUS_TEXT = "Thinking…";

const EMPTY: ChatStoreState = { entries: [], draft: "", sending: false };

let state: ChatStoreState = EMPTY;
let nextId = 0;
const listeners = new Set<() => void>();

function set(next: ChatStoreState): void {
  state = next;
  listeners.forEach((listener) => listener());
}

function subscribe(onChange: () => void): () => void {
  listeners.add(onChange);
  return () => listeners.delete(onChange);
}

function snapshot(): ChatStoreState {
  return state;
}

export function useChatStore(): ChatStoreState {
  return useSyncExternalStore(subscribe, snapshot);
}

export function setDraft(draft: string): void {
  set({ ...state, draft });
}

/** Generic append (Story 9.2) — any future `StreamEntry` kind (Story 9.3's `"sandbox-finale"`) reuses this unchanged. */
export function appendStreamEntry(entry: Omit<StreamEntry, "id">): string {
  const id = `entry-${++nextId}`;
  set({ ...state, entries: [...state.entries, { ...entry, id } as StreamEntry] });
  return id;
}

/** Generic patch (Story 9.2) — merges `patch` onto the entry with this `id`, regardless of kind. */
export function updateStreamEntry(id: string, patch: Partial<StreamEntry>): void {
  set({ ...state, entries: state.entries.map((e) => (e.id === id ? ({ ...e, ...patch } as StreamEntry) : e)) });
}

function messageEntries(entries: readonly StreamEntry[]): ReadonlyArray<Extract<StreamEntry, { kind: "message" }>> {
  return entries.filter((e): e is Extract<StreamEntry, { kind: "message" }> => e.kind === "message");
}

function patchMessage(id: string, patch: (message: ChatViewMessage) => Partial<ChatViewMessage>): void {
  set({
    ...state,
    entries: state.entries.map((e) => (e.kind === "message" && e.message.id === id ? { ...e, message: { ...e.message, ...patch(e.message) } } : e)),
  });
}

function appendMessage(message: ChatViewMessage): void {
  set({ ...state, entries: [...state.entries, { kind: "message", id: message.id, message }] });
}

/** The transcript as `ChatTurnRequest.history` — "message" entries only, a card is never appended to the LLM-facing transcript. */
function historyOf(entries: readonly StreamEntry[]): ChatTurnRequest["history"] {
  return messageEntries(entries)
    .map((e) => e.message)
    .filter((m) => m.status !== "streaming" && m.text.trim() !== "")
    .map((m) => ({ role: m.role, content: m.text }));
}

export async function send(message: string): Promise<void> {
  const trimmed = message.trim();
  if (trimmed === "" || state.sending) return;

  const userId = `chat-${++nextId}`;
  const assistantId = `chat-${++nextId}`;
  const request: ChatTurnRequest = { message: trimmed, history: [...historyOf(state.entries), { role: "user", content: trimmed }] };
  appendMessage({ id: userId, role: "user", text: trimmed, receipts: [], status: "done" });
  appendMessage({ id: assistantId, role: "assistant", text: "", receipts: [], status: "streaming", statusText: INITIAL_STATUS_TEXT });
  set({ ...state, draft: "", sending: true });

  const onEvent = (event: ChatStreamEvent): void => {
    switch (event.type) {
      case "status":
        patchMessage(assistantId, () => ({ statusText: event.text }));
        return;
      case "delta":
        patchMessage(assistantId, (m) => ({ text: m.text + event.text }));
        return;
      case "done":
        patchMessage(assistantId, () => ({
          text: event.response.reply,
          receipts: event.response.receipts,
          status: "done",
          ...(event.response.question ? { question: event.response.question } : {}),
        }));
        if (event.response.sandboxCard) startSandbox(event.response.sandboxCard);
        set({ ...state, sending: false });
        return;
      case "error":
        patchMessage(assistantId, () => ({ status: "error", errorText: event.error.message }));
        set({ ...state, sending: false });
        return;
    }
  };

  try {
    await streamChat(request, { onEvent });
  } catch {
    const partial = messageEntries(state.entries).find((e) => e.id === assistantId)?.message;
    if (partial && partial.text !== "") {
      patchMessage(assistantId, () => ({ status: "error" }));
      set({ ...state, sending: false });
      return;
    }
    set({
      entries: state.entries.filter((e) => !(e.kind === "message" && (e.id === userId || e.id === assistantId))),
      draft: state.draft === "" ? trimmed : state.draft,
      sending: false,
    });
    addLocalFailureNotice("Couldn't reach Yoh. Your message is back in the box to try again.");
  }
}

export function recordAnsweredOpenItem(youText: string, yoh: { message?: string; receipts: readonly string[] }): void {
  appendMessage({ id: `chat-${++nextId}`, role: "user", text: youText, receipts: [], status: "done" });
  appendMessage({ id: `chat-${++nextId}`, role: "assistant", text: yoh.message ?? "", receipts: yoh.receipts, status: "done" });
}

/** Test-only: clears the module-level transcript between tests. Never called from production code. */
export function __resetChatStoreForTests(): void {
  state = EMPTY;
  nextId = 0;
}

This is a genuine two-way module reference between these two sibling files — safe here because neither call happens at module-evaluation time: `chatStore.ts` calls `startSandbox` only inside `send()`'s async `"done"` handler, and `sandbox.ts` calls `appendStreamEntry`/`updateStreamEntry` only inside its own exported functions' bodies (never at either file's top level). /**
 * web/src/lib/sandboxClient.ts
 *
 * Story 9.2: the three `/sandbox` calls, over the typed Hono RPC client —
 * mirrors `checkOff.ts`'s exact `settle<T>` convention verbatim. Every call
 * resolves to an outcome and never throws: a rejected request and an
 * `{ok:false}` envelope both come back as `{ok:false, message}`. Story 9.3
 * adds a fourth sibling export, `requestSandboxFinish`, to this same file.
 */
import { apiClient } from "./apiClient.ts";
import type { SandboxSaveRequest, SandboxSkipRequest, SandboxStartResponse, SandboxSaveResponse, SandboxSkipResponse } from "../../../src/types/api.ts";

export type SandboxOutcomeResult<T> = { readonly ok: true; readonly value: T } | { readonly ok: false; readonly message: string };

async function settle<T>(request: () => Promise<{ json(): Promise<unknown> }>): Promise<SandboxOutcomeResult<T>> {
  try {
    const res = await request();
    const result = (await res.json()) as { ok: true; value: T } | { ok: false; error: { message: string } };
    return result.ok ? { ok: true, value: result.value } : { ok: false, message: result.error.message };
  } catch (err) {
    return { ok: false, message: err instanceof Error ? err.message : String(err) };
  }
}

export function requestSandboxStart(exclude?: readonly string[]): Promise<SandboxOutcomeResult<SandboxStartResponse>> {
  return settle(() => apiClient.api.sandbox.start.$post({ json: exclude ? { exclude } : {} }));
}

export function requestSandboxSave(taskId: string, body: SandboxSaveRequest): Promise<SandboxOutcomeResult<SandboxSaveResponse>> {
  return settle(() => apiClient.api.sandbox[":taskId"].save.$post({ param: { taskId }, json: body }));
}

export function requestSandboxSkip(taskId: string, body: SandboxSkipRequest): Promise<SandboxOutcomeResult<SandboxSkipResponse>> {
  return settle(() => apiClient.api.sandbox[":taskId"].skip.$post({ param: { taskId }, json: body }));
}

import { useSyncExternalStore } from "react";
import { appendStreamEntry, updateStreamEntry } from "./chatStore.ts";
import { requestSandboxSave, requestSandboxSkip } from "./sandboxClient.ts";
import type { SandboxCardView } from "../../../src/types/api.ts";

interface SandboxOutcomeRecord {
  readonly taskId: string;
  readonly taskTitle: string;
  readonly ok: boolean;
}

export interface SandboxSessionState {
  readonly card: SandboxCardView | undefined;
  readonly exclude: readonly string[];
  readonly outcomes: readonly SandboxOutcomeRecord[];
}

const EMPTY: SandboxSessionState = { card: undefined, exclude: [], outcomes: [] };
let state: SandboxSessionState = EMPTY;
/** Internal-only: which chatStore entry the CURRENT `state.card` corresponds to. Exactly one is ever pending at a time. */
let entryId: string | undefined;
const listeners = new Set<() => void>();

function set(next: SandboxSessionState): void {
  state = next;
  listeners.forEach((l) => l());
}
function subscribe(onChange: () => void): () => void {
  listeners.add(onChange);
  return () => listeners.delete(onChange);
}
function snapshot(): SandboxSessionState {
  return state;
}

export function useSandboxSession(): SandboxSessionState {
  return useSyncExternalStore(subscribe, snapshot);
}

export function startSandbox(card: SandboxCardView): void {
  entryId = appendStreamEntry({ kind: "sandbox-card", view: card, status: "pending" });
  set({ card, exclude: [], outcomes: [] });
}

function settleAndAdvance(next: SandboxCardView | undefined, patch: { status: "saved" | "skipped" | "failed"; receipt?: string }): void {
  if (entryId) updateStreamEntry(entryId, patch);
  entryId = next ? appendStreamEntry({ kind: "sandbox-card", view: next, status: "pending" }) : undefined;
}

export async function saveCard(input: { dueDate: string; estimatedDurationMinutes: string; area?: string; energy?: string }): Promise<void> {
  const card = state.card;
  if (!card) return;
  const result = await requestSandboxSave(card.taskId, { ...input, exclude: state.exclude });
  if (!result.ok) {
    // FR-38: an unresolvable value re-prompts on THIS card — it stays
    // pending, never advances, never counts as an outcome. The card's own
    // component renders `result`'s message inline (SandboxCard.tsx, Task 8).
    return;
  }
  settleAndAdvance(result.value.next, { status: "saved", receipt: result.value.receipt });
  set({
    card: result.value.next,
    exclude: [...state.exclude, card.taskId],
    outcomes: [...state.outcomes, { taskId: card.taskId, taskTitle: card.taskTitle, ok: true }],
  });
  if (!result.value.next) await finishSandbox();
}

export async function skipCard(): Promise<void> {
  const card = state.card;
  if (!card) return;
  const result = await requestSandboxSkip(card.taskId, { exclude: state.exclude });
  const next = result.ok ? result.value.next : state.card; // a network hiccup on skip leaves the card in place — nothing was written either way
  if (result.ok) {
    settleAndAdvance(next, { status: "skipped" });
    set({ card: next, exclude: [...state.exclude, card.taskId], outcomes: state.outcomes });
    if (!next) await finishSandbox();
  }
}

/**
 * Story 9.2 scope: a quiet reset — matches the "all-skip session ends
 * quietly, no Finale, no server round trip, no notification" ruling for
 * the zero-saves case, and is the placeholder every OTHER case (>=1 save)
 * falls back to until Story 9.3 replaces this body with the real `POST
 * /api/sandbox/finish` call, the Finale bar `StreamEntry`, and the reward
 * chime. Never throws; safe to call unconditionally.
 */
export async function finishSandbox(): Promise<void> {
  entryId = undefined;
  set(EMPTY);
}

/** Test-only: clears module-level singleton state between tests. Never called from production code. */
export function __resetSandboxForTests(): void {
  entryId = undefined;
  state = EMPTY;
}
```

Create `web/src/components/SandboxCard.tsx`:

```tsx
/**
 * web/src/components/SandboxCard.tsx
 *
 * Story 9.2, UX-DR39: one Sandbox Card — a `neumorphic-card` at `rounded-md`
 * rendered inline in the Chat stream. Task name in `typography.title`, Due
 * Date/Estimated Duration rimmed and required, Area/Energy optional, a
 * Secondary "Skip" and a Primary "Save" (disabled until both required
 * fields are filled — a client-side convenience only; the server re-checks
 * regardless, AD-17), and "N remaining" in tabular numerals. A rejected save
 * (an unresolvable Area/Energy) re-prompts INLINE, on this same card,
 * showing the server's own message — the card never advances or leaves
 * history on a rejection (FR-38).
 */
import { useState } from "react";
import { saveCard, skipCard } from "../lib/sandbox.ts";
import { useReducedMotion } from "../hooks/useReducedMotion.ts";
import type { SandboxCardView } from "../../../src/types/api.ts";

export interface SandboxCardProps {
  readonly view: SandboxCardView;
  readonly status: "pending" | "saved" | "skipped" | "failed";
  readonly receipt?: string;
}

const RIM_INPUT =
  "h-10 w-full min-w-0 rounded-md border-[length:var(--rim-width)] border-accent-solid bg-surface-sunken px-3 font-body text-small text-ink-primary shadow-inset outline-none " +
  "focus-visible:outline-[length:var(--focus-ring-width)] focus-visible:outline-offset-2 focus-visible:outline-accent-solid";
const PLAIN_INPUT =
  "h-10 w-full min-w-0 rounded-md border-[length:var(--rim-width)] border-rim-interactive bg-surface-raised px-3 font-body text-small text-ink-primary shadow-extruded-sm outline-none " +
  "focus-visible:outline-[length:var(--focus-ring-width)] focus-visible:outline-offset-2 focus-visible:outline-accent-solid";
const PRIMARY_BUTTON =
  "h-[42px] rounded-full border-transparent bg-gradient-to-br from-accent-gradient-start to-accent-gradient-end px-5 font-bold text-on-accent-solid shadow-extruded-sm disabled:opacity-40 " +
  "focus-visible:outline-[length:var(--focus-ring-width)] focus-visible:outline-offset-2 focus-visible:outline-accent-solid";
const SECONDARY_BUTTON =
  "h-[42px] rounded-full border-[length:var(--rim-width)] border-rim-interactive bg-surface-raised px-5 font-bold text-ink-primary shadow-extruded-sm disabled:opacity-40 " +
  "focus-visible:outline-[length:var(--focus-ring-width)] focus-visible:outline-offset-2 focus-visible:outline-accent-solid";

const SETTLED_LABEL: Record<Exclude<SandboxCardProps["status"], "pending">, string> = {
  saved: "Saved",
  skipped: "Skipped",
  failed: "Couldn't save",
};

export function SandboxCard({ view, status, receipt }: SandboxCardProps): React.JSX.Element {
  const reducedMotion = useReducedMotion();
  const [dueDate, setDueDate] = useState(view.dueDate ?? "");
  const [estimatedDurationMinutes, setEstimatedDurationMinutes] = useState(view.estimatedDurationMinutes !== undefined ? String(view.estimatedDurationMinutes) : "");
  const [area, setArea] = useState(view.area ?? "");
  const [energy, setEnergy] = useState(view.energy ?? "");
  const [busy, setBusy] = useState(false);
  const [errorText, setErrorText] = useState<string | undefined>(undefined);
  const [justSaved, setJustSaved] = useState(false);

  if (status !== "pending") {
    return (
      <div
        data-testid="sandbox-card"
        aria-live="polite"
        className={`flex flex-col gap-1 rounded-md bg-surface-raised p-5 font-body text-body text-ink-primary shadow-extruded-sm ${!reducedMotion && status === "saved" ? "sandbox-card-save-pulse" : ""}`}
      >
        <p className="m-0 font-medium text-title">{view.taskTitle}</p>
        <p className="m-0 text-ink-secondary">{SETTLED_LABEL[status]}</p>
        {receipt && <p className="m-0 font-body text-caption text-ink-secondary">{receipt}</p>}
      </div>
    );
  }

  const canSave = dueDate.trim() !== "" && estimatedDurationMinutes.trim() !== "";

  const onSave = async (): Promise<void> => {
    setBusy(true);
    setErrorText(undefined);
    await saveCard({
      dueDate,
      estimatedDurationMinutes,
      ...(area.trim() !== "" ? { area: area.trim() } : {}),
      ...(energy.trim() !== "" ? { energy: energy.trim() } : {}),
    });
    setBusy(false);
    // A rejection leaves this same card mounted (its own StreamEntry stays
    // "pending") — sandbox.ts's saveCard already handled the outcome; this
    // component has no direct signal of "it failed" other than remaining
    // pending, so a locally-tracked flag drives the inline re-prompt copy.
    setJustSaved(true);
  };

  const onSkip = (): void => {
    void skipCard();
  };

  return (
    <div data-testid="sandbox-card" className="flex flex-col gap-3 rounded-md bg-surface-raised p-5 font-body text-body text-ink-primary shadow-extruded-sm">
      <p className="m-0 font-medium text-title">{view.taskTitle}</p>
      {justSaved && errorText && (
        <p role="alert" className="m-0 text-caption text-ink-danger">
          {errorText}
        </p>
      )}
      <div className="grid grid-cols-2 gap-3">
        <label className="flex flex-col gap-1 text-caption text-ink-secondary">
          Due Date
          <input type="date" aria-label="Due Date" value={dueDate} onChange={(e) => setDueDate(e.target.value)} className={RIM_INPUT} />
        </label>
        <label className="flex flex-col gap-1 text-caption text-ink-secondary">
          Estimated Duration (minutes)
          <input
            type="number"
            inputMode="numeric"
            min={1}
            aria-label="Estimated Duration"
            value={estimatedDurationMinutes}
            onChange={(e) => setEstimatedDurationMinutes(e.target.value)}
            className={RIM_INPUT}
          />
        </label>
        <label className="flex flex-col gap-1 text-caption text-ink-secondary">
          Area (optional)
          <input type="text" aria-label="Area" value={area} onChange={(e) => setArea(e.target.value)} className={PLAIN_INPUT} />
        </label>
        <label className="flex flex-col gap-1 text-caption text-ink-secondary">
          Energy (optional)
          <input type="text" aria-label="Energy" placeholder="low / medium / high" value={energy} onChange={(e) => setEnergy(e.target.value)} className={PLAIN_INPUT} />
        </label>
      </div>
      <div className="flex items-center justify-between">
        <span className="font-body text-numerals tabular-nums text-ink-secondary">{view.remaining} remaining</span>
        <div className="flex gap-2">
          <button type="button" disabled={busy} onClick={onSkip} className={SECONDARY_BUTTON}>
            Skip
          </button>
          <button type="button" disabled={busy || !canSave} onClick={() => void onSave()} className={PRIMARY_BUTTON}>
            Save
          </button>
        </div>
      </div>
    </div>
  );
}
```

`errorText`'s inline re-prompt above is written defensively (`sandbox.ts`'s `saveCard` does not currently surface the rejection message back to the calling component — see Task 7's own doc comment: on a rejection it simply returns, leaving the card pending). **Flagging for the controller:** to genuinely show the server's rejection message inline (rather than just "still pending, try again"), `sandbox.ts`'s `saveCard` needs to return its own outcome (e.g. `Promise<{ok:true} | {ok:false; message:string}>`) instead of `Promise<void>`, and this component reads that return value directly instead of the `justSaved`/`errorText` local-state workaround shown above. This plan ships the workaround (a plain "still pending" state, silently re-editable) to keep Task 7's signature exactly matching what Task 3's own plan already assumed (`saveCard(input): Promise<void>`, Assumption #4) — widening it to return an outcome is a small, backward-compatible change (Task 3 never reads `saveCard`'s return value) the controller can approve in a follow-up pass without touching anything else in this plan.
