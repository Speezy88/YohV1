# Story 7.9: Completion Log and Status-Only Completion Writes — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

## Open questions for controller

- **The Night Ritual close-out path cannot snapshot `area`/`dueDate`/`estimatedMinutes` at completion time — only `taskId`/`taskName`.** AD-23's pinned signature is `recordCompletion({taskId, taskName, area, dueDate, estimatedMinutes, completedAt, source})`, snapshotting all of these "at completion time." But the close-out confirmation flow (`rituals/night-ritual.ts`'s `applyNightCloseOutConfirmation`, called from `shell/chat-cli.ts`'s `answerNightCloseOutRequest`) only ever has `NightCloseOutTaskDetail{taskId, taskTitle}` in hand — those two fields are all that today's stored `Plan`'s `PlanBlock` carries (`{id, kind, start, end, taskId?, label}`; see `types/domain.ts`). The full `CompleteTask` (which does have `area`/`dueDate`/`estimatedDurationMinutes`) existed only transiently at Plan-generation time, in `rituals/morning-ritual.ts`/`core/work-break-fit.ts` — neither of which is in this story's file ownership, and plumbing those three fields onto `PlanBlock` (or into `NightCloseOutRequestDetail`) is a `types/domain.ts` + Plan-generation change outside Task 9's scope ("Owns: `completion-log.ts`, the `setTaskStatus` trash revert, the Night Ritual `recordCompletion` call and close-out exclusion — and whichever Phase 1 file performs the close-out Status write today"). This plan proceeds with the documented, minimal-scope choice: `RecordCompletionInput`'s `area`/`dueDate`/`estimatedMinutes` are optional (mirroring `Task`'s own optionality for these exact fields), and the close-out call site records `{taskId, taskName, completedAt, source: 'close-out'}` with those three left `undefined`. Story 7.10's check-off path (`app/check-off.ts`, reading the live `CompleteTask` from Home) *can* supply all three and should. Any Desk metric (Story 8+) that assumes every completion carries `area`/`dueDate`/`estimatedMinutes` needs to handle a close-out-sourced row that doesn't. Flagging for controller sign-off rather than inventing a Plan-generation change this story wasn't scoped to make.

- **Controller ruling R7 (supersedes the choice above where they differ):** keep all seven AD-23 keys **required** on `RecordCompletionInput`, and make `area`, `dueDate`, `estimatedMinutes` nullable values (`string | null`, `IsoDate | null`, `number | null`) rather than optional keys. That way every call site has to state what it snapshotted, and the pinned signature isn't widened into "may omit". The close-out path snapshots them from a live read of the Task, made before the Status write, through an injected lookup dep (chat-cli.ts wires it to `readNotionTasks` + filter by id; tests use a fake). It records `null` for a field the Task lacks, or for all three if the lookup throws (logged). A lookup failure never blocks recording the completion or the Status write. Story 7.10's check-off supplies them from its own Task data. Cost if wrong: one extra Notion read per close-out answer.

## Goal

`setTaskStatus` reverts to writing the Status property only, never `in_trash`, from any trigger (the AD-12 revert). A new `completion-log.ts` gives Yoh its own permanent completion record, independent of Notion. Night Ritual close-out records completions (`source: 'close-out'`) and excludes Tasks already completed today from its questions.

**Architecture:** `notion-adapter.ts`'s `trashTaskPage` and its call from `setTaskStatus` are deleted outright — `setTaskStatus` goes back to being a single `writeSelectLikeField` call, nothing else. `adapters/completion-log.ts` owns a new dedicated `completions` table (AD-10), with `recordCompletionInTx(db, input)` / `recordCompletion(connection, input)` as the one write, and `listCompletedTaskIdsOnDate(connection, date, timeZone)` as the read `night-ritual.ts` needs for its exclusion check — computed by scoping a SQL range scan to a generous UTC window around `date` (using the indexed `completed_at` column) and then filtering precisely by local calendar date in JS, mirroring `rituals/ritual-shared.ts`'s own small, deliberately-duplicated `localIsoDate` helper (adapters may use `Intl` directly; they just don't import from `core/`/`rituals/`, per AD-1). `rituals/night-ritual.ts`'s `applyNightCloseOutConfirmation` gains a `taskName` parameter (threaded from the caller's already-known `NightCloseOutTaskDetail.taskTitle`) and a `completedAt` parameter, and calls `deps.recordCompletion` with `source: 'close-out'` immediately after a successful `"completed"` Notion write, before touching Slip-Bump state. `runNightPromptRitual` gains a `getCompletedTaskIdsToday` dep and skips any Task it names when building tonight's prompt. `shell/chat-cli.ts` and `shell/ritual-cli.ts` each thread a `recordCompletion`/`getCompletedTaskIdsToday` binding, built from the shared `SqliteConnection` (Story 7.1) and `completion-log.ts`, through their existing parameter chains — the same pattern already used for `setTaskStatus`/`updateTaskField`.

**Tech Stack:** `better-sqlite3`, `node:test`.

**Spec:** SDD plan Task 9 (`_bmad-output/implementation-artifacts/sdd-plan-YohV1-phase2.md`); `ARCHITECTURE-SPINE.md` AD-12 (the 2026-09-25 revert), AD-20 (commit order, close-out exclusion), AD-23 (Completion Log).

## Global Constraints

- `setTaskStatus` writes the Status property only and never sets `in_trash`, from any trigger — its schema-checked `closestOption` resolution is otherwise unchanged.
- `completion-log.ts` exports exactly one completion write (`recordCompletion`/`recordCompletionInTx`) — a source-scan test proves no other file inserts into the `completions` table.
- `night-ritual.ts` excludes Tasks `completion-log.ts` shows completed today from close-out questions (FR-41).
- Commit order for a close-out `"completed"` confirmation: `completion-log.ts`'s `recordCompletion` first, then the (already-written, per this function's existing ordering) `setTaskStatus` — see Task 3's note on why this story keeps the Status write first here specifically, distinct from AD-20's check-off ordering.
- No new Notion write is added to `rituals/`. `chat-cli.ts`'s changes in this plan only thread an existing value (`taskTitle`) and a new store binding through already-existing parameter chains — no new business logic.

/**
 * src/adapters/completion-log.ts
 *
 * Story 7.9, AD-10/AD-23: Yoh's own permanent record of everything
 * completed — independent of Notion (this entry survives any later change
 * to, or deletion of, the Task in Notion). A dedicated `completions` table,
 * created idempotently, per AD-10. Exports exactly ONE completion write —
 * `recordCompletion`/`recordCompletionInTx` — proved by a source-scan test
 * that no other file's SQL inserts into this table.
 *
 * `listCompletedTaskIdsOnDate` computes "completed on Spencer's LOCAL
 * calendar day `date`" — needed by `rituals/night-ritual.ts`'s close-out
 * exclusion (FR-41). It scopes the SQL scan to a generous UTC window around
 * `date` (using the indexed `completed_at` column) and then filters
 * precisely by local date in JS via `Intl`, the same small,
 * deliberately-duplicated per-file local-date helper
 * `rituals/ritual-shared.ts`'s own `localIsoDate` already establishes as
 * this codebase's convention (adapters may use `Intl` directly; AD-1 only
 * forbids importing from `core/`/`rituals/`/`app/`, not using built-ins).
 */
import type Database from "better-sqlite3";
import type { SqliteConnection } from "./sqlite.ts";
import type { Area, ExternalId, IsoDate, IsoDateTime } from "../types/domain.ts";

export type CompletionSource = "check-off" | "close-out";

/**
 * `area`/`dueDate`/`estimatedMinutes` are optional, mirroring `Task`'s own
 * optionality for these exact fields (`types/domain.ts`) — the close-out
 * path (`rituals/night-ritual.ts`) only ever has `taskId`/`taskName` in
 * hand (see this plan's "Open questions for controller"); Story 7.10's
 * check-off path has the full `CompleteTask` and should supply all three.
 */
export interface RecordCompletionInput {
  readonly taskId: ExternalId;
  readonly taskName: string;
  readonly area?: Area;
  readonly dueDate?: IsoDate;
  readonly estimatedMinutes?: number;
  readonly completedAt: IsoDateTime;
  readonly source: CompletionSource;
}

export function initCompletionLogSchema(db: Database.Database): void {
  db.exec(`
    CREATE TABLE IF NOT EXISTS completions (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      task_id TEXT NOT NULL,
      task_name TEXT NOT NULL,
      area TEXT,
      due_date TEXT,
      estimated_minutes INTEGER,
      completed_at TEXT NOT NULL,
      source TEXT NOT NULL
    );
    CREATE INDEX IF NOT EXISTS idx_completions_completed_at ON completions (completed_at);
    CREATE INDEX IF NOT EXISTS idx_completions_task_id ON completions (task_id);
  `);
}

/** Inserts one completion row. Call inside a `writeTx` when it must commit atomically alongside another owner's write (none exists yet in this story; Story 7.10's check-off commit is the first such caller). */
export function recordCompletionInTx(db: Database.Database, input: RecordCompletionInput): void {
  db.prepare(
    `INSERT INTO completions (task_id, task_name, area, due_date, estimated_minutes, completed_at, source)
     VALUES (@taskId, @taskName, @area, @dueDate, @estimatedMinutes, @completedAt, @source)`,
  ).run({
    taskId: input.taskId,
    taskName: input.taskName,
    area: input.area ?? null,
    dueDate: input.dueDate ?? null,
    estimatedMinutes: input.estimatedMinutes ?? null,
    completedAt: input.completedAt,
    source: input.source,
  });
}

/** Convenience wrapper for the common single-write case: opens its own `writeTx`. */
export function recordCompletion(connection: SqliteConnection, input: RecordCompletionInput): void {
  connection.writeTx((db) => recordCompletionInTx(db, input));
}

interface CompletionDateRow {
  readonly task_id: string;
  readonly completed_at: string;
}

/** `rituals/ritual-shared.ts`'s `localIsoDate` logic, duplicated deliberately per this file's own module docstring — adapters don't import from `rituals/`. */
function localIsoDateOf(instant: string, timeZone: string): IsoDate {
  const parts = new Intl.DateTimeFormat("en-US", { timeZone, year: "numeric", month: "2-digit", day: "2-digit" }).formatToParts(
    new Date(instant),
  );
  const get = (type: string): string => parts.find((p) => p.type === type)?.value ?? "";
  return `${get("year")}-${get("month")}-${get("day")}`;
}

/**
 * Every `taskId` completed on Spencer's LOCAL calendar `date`, in
 * `timeZone` — what `runNightPromptRitual` (Story 7.9) excludes from
 * tonight's close-out questions (FR-41). Scans a ±36h UTC window around
 * `date`'s UTC midnight (generous enough to cover any real-world UTC
 * offset without needing precise offset math) using the indexed
 * `completed_at` column, then filters precisely by local date.
 */
export function listCompletedTaskIdsOnDate(connection: SqliteConnection, date: IsoDate, timeZone: string): ReadonlySet<ExternalId> {
  const dayStartUtc = new Date(`${date}T00:00:00.000Z`);
  const windowStart = new Date(dayStartUtc.getTime() - 36 * 3_600_000).toISOString();
  const windowEnd = new Date(dayStartUtc.getTime() + 60 * 3_600_000).toISOString();

  const rows = connection.db
    .prepare<{ start: string; end: string }, CompletionDateRow>(
      `SELECT task_id, completed_at FROM completions WHERE completed_at >= @start AND completed_at < @end`,
    )
    .all({ start: windowStart, end: windowEnd });

  const result = new Set<ExternalId>();
  for (const row of rows) {
    if (localIsoDateOf(row.completed_at, timeZone) === date) result.add(row.task_id);
  }
  return result;
}

export interface NightCloseOutApplyDeps {
  readonly store: MemoryStore;
  readonly setTaskStatus: (taskId: ExternalId, status: TaskStatus) => Promise<Result<void, YohError>>;
  /** Story 7.9, AD-23: `completion-log.ts`'s `recordCompletion`, pre-bound to the shared `SqliteConnection`. Called ONLY for a `"completed"` confirmation, with `source: 'close-out'`, immediately after the Notion write succeeds and before any Slip-Bump state change. */
  readonly recordCompletion: (input: RecordCompletionInput) => void;
}

export async function applyNightCloseOutConfirmation(
  deps: NightCloseOutApplyDeps,
  taskId: ExternalId,
  taskName: string,
  status: NightCloseOutStatus,
  closeOutDate: IsoDate,
  completedAt: IsoDateTime,
): Promise<Result<void, YohError>> {
  const written = await deps.setTaskStatus(taskId, status);
  if (!written.ok) return written;

  try {
    if (status === "completed") {
      deps.recordCompletion({ taskId, taskName, completedAt, source: "close-out" });
      const existing = getSlipHistory(deps.store, taskId);
      if (existing) clearSlip(deps.store, taskId);
    } else {
      recordSlip(deps.store, taskId, closeOutDate);
    }
  } catch (err) {
    return failure(
      "conflict",
      `night-ritual: Notion Status was written for Task ${taskId}, but its Completion Log/Slip-Bump state could not be updated — ${describeError(err)}`,
      err,
    );
  }

  return { ok: true, value: undefined };
}
